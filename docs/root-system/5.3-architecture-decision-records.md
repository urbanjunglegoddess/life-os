# Architecture Decision Records (ADRs)

## 📋 Description

Preserves the reasoning behind each significant technical choice for future maintainers — context, decision, alternatives, and consequences. One ADR per decision.

## ❓ Guiding Questions

◆ What decision is being made, and in what context?
◆ What alternatives were considered?
◆ What are the consequences (good and bad)?
◆ What is the decision's status?

## ✏️ Activities

1. State context and the decision.
2. List alternatives.
3. Record consequences.
4. Set status and date.

## 📐 ADR Format

| Field | Entry |
| ---| --- |
| Context | What forced the decision |
| Decision | What was chosen |
| Alternatives | What was rejected |
| Consequences | What we now live with |
| Status / Date | Where it stands |

#### ADR-0001: Native (Expo) over web PWA

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | platform, mobile |

**Context.** The app must be the daily operating surface on a phone, with push that fires reliably, real biometrics on sensitive modules, and genuine offline capture. The builder's existing skills lean web.

**Considered options.** 1. React Native via Expo. 2. Next.js PWA (simpler, skill-aligned).

**Decision.** **Expo.** iOS reliability for push, real biometrics, and offline are must-haves a PWA can't deliver. A web companion comes later via React Native Web on the same code.

**Consequences.**
*   👍 Real push, real biometrics, real offline; OTA updates; EAS cloud builds mean no local Mac.
*   👎 Slower to ship than a PWA; a native build pipeline to learn and maintain.
*   ⚖️ The web companion is deferred to Phase 7 rather than free on day one.

#### ADR-0002: Supabase over a custom backend

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | backend, data, infra |

**Context.** A solo, agentic build on free tiers needs a backend that supplies database, auth, storage, realtime, functions, and scheduling without becoming a second project.

**Considered options.** 1. Supabase. 2. Hand-rolled Node + Postgres. 3. Firebase.

**Decision.** **Supabase.** Postgres + RLS + Auth + Storage + Realtime + Edge Functions + pg\_cron in one sovereign, exportable, free-tier service — excellent for solo and agentic builds. Postgres in particular gives real relations and generated columns, which is what kills the Notion chained-formula problem.

**Consequences.**
*   👍 One service, one system of record, exportable and owned; RLS doubles as the authorization layer.
*   👎 Platform dependency on Supabase's roadmap and free-tier limits.
*   ⚖️ Firebase's document model was never a fit — the whole point is relational computation.

#### ADR-0003: Drop Payload CMS

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | content, infra |
| Supersedes | The Payload-owned `cms_*` model in the original Architecture doc (page 03) |

**Context.** The original design gave Payload CMS ownership of catalog and library content — recipes, resources, media, affirmations, digital asset catalog, content templates — running against the same Supabase Postgres via its Postgres adapter. That created a second writer and a second server.

**Considered options.** 1. Keep Payload for a content admin UI. 2. Drop it; in-app editors plus Supabase Studio.

**Decision.** **Drop Payload CMS.** It is a second server to host, auth, and maintain for a tiny payoff. Catalog content gets in-app editors, and Supabase Studio covers bulk edits. **It also removes the two-writers risk entirely.**

**Consequences.**
*   👍 One server, one writer path, lower cost, less surface to secure. The `cms_*` prefix and the one-writer-per-table rule are retired.
*   👎 Curated content editing must be built in-app rather than inherited from a CMS admin.
*   ⚖️ Any future need for a true content admin reopens this — write a superseding ADR, don't reintroduce it quietly.

**Follow-ups.** Remove `/payload` from the repo layout. Re-home the former `cms_*` tables as ordinary app tables in 5.6, tenant-scoped like everything else.

#### ADR-0004: Three-layer multi-tenancy from day one

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | security, data, product |
| Supersedes | The single-user / "multi-profile-ready schema" framing in the original Charter and Architecture docs |

**Context.** v1 has exactly one user. A commercial Freelance Life OS release is a stated future goal. The question is whether to build tenancy now or retrofit it.

**Considered options.** 1. Single-user now, retrofit tenancy later. 2. Three nested layers from day one.

**Decision.** **Three layers from day one** — **tenant** (account; the RLS wall; isolates Omegea from any future customer) → **profile** (person; Omegea and each child) → **entity** (business; Empire, UJG, JMR). Every row is scoped by `tenant_id` always, plus `profile_id` and/or `entity_id` where relevant.

**Consequences.**
*   👍 The commercial release becomes a config flag on the same codebase, not a rewrite.
*   👎 Every table, query, and policy carries tenancy overhead from the first migration, for a benefit that is invisible in v1.
*   ⚖️ Correctness must be proven, not assumed — the tenant-isolation test is a release gate.

**Validation.** Test 1 of the failure chain (7.1): given a user, when querying another tenant's row, then RLS blocks it with no leak. This gates every release.

#### ADR-0005: Shared action-spine architecture

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | architecture, data |
| Supersedes | The flat 17-module model in the original PRD |

**Context.** The app must show the control of a whole life and drive cross-hub action. A per-hub siloed data model cannot do either — it produces a set of trackers that never talk to each other.

**Considered options.** 1. Per-hub siloed data. 2. A shared spine of core entities that every hub inherits.

**Decision.** **Shared action-spine.** One record, many views. The spine — Actions, Events, Money ledger, People/CRM, Goals & Missions, Notes, Areas/Tags, Automation + Notifications, Templates/Routines — is an inherited platform layer used through a shared data-access layer. **Actions are the universal unit:** every plan, goal, bill, routine, and ritual decomposes into Actions carrying a do-now deep link, and progress rolls up from completed Actions rather than being typed by hand.

Hubs are bounded contexts owning private tables. **No hub reaches into a sibling hub's tables** — cross-hub needs go through the spine or an explicit interface. This is shared-kernel, not distributed services: one Postgres, one codebase.

**Consequences.**
*   👍 The cockpit can genuinely slice the whole life; hubs become swappable lenses; cross-hub automation is natural rather than bolted on.
*   👎 The spine must be right before hubs are built — it is the blocking dependency for Phase 2.
*   ⚖️ Discipline cost: the no-sibling-reads rule has to be enforced in review, or the shared kernel rots into a distributed monolith inside one app.

#### ADR-0006: Robust + cheap, sacrifice fast

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | strategy |

**Context.** Fast / cheap / robust — pick two.

**Decision.** **ROBUST and CHEAP. FAST is the deliberate sacrifice.** The app holds a whole life's data, must be owned and sovereign, and must be multi-tenant-ready to become a product, so robust is non-negotiable. Solo and budget-bound means free tiers, so cheap is forced and fine.

**Consequences.**
*   👍 Durable infrastructure rather than a spike; correctness and ownership bought with time.
*   👎 A native build pipeline and a real data layer are slower than a throwaway PWA. Ship dates are effort-based, never calendar-based.
*   ⚖️ Any pressure to "just ship something faster" is a request to break this ADR — treat it as one.

#### ADR-0007: The spine is the seam; defer deeper abstraction

| Field | Value |
| ---| --- |
| Status | Accepted |
| Tags | architecture |

**Context.** The thing most likely to change within ~3 months is the hub feature set — which modules exist, what each tracks, and final tech choices that solidify later. The architecture needs a seam that absorbs that churn.

**Decision.** **The shared spine is the stable boundary; hubs are swappable lenses over it.** New or changed hubs read and write the same core through the data-access layer, so a hub can be added, reshaped, or dropped without touching the core. **Defer deeper abstraction until a second tenant — the commercial release — actually exercises it.**

**Consequences.**
*   👍 Hub churn is cheap; the core stays stable; no speculative generality.
*   👎 Some abstraction will have to be added later under real pressure rather than designed up front.
*   ⚖️ Revisit trigger: the first real second tenant.

#### ADR-0008: Lifestyle Vault stays one bounded context

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-08-23 |
| Deciders | Omegea Hunter |
| Tags | architecture, information-architecture |

**Context and problem statement.** The crawl of the source Notion system found that "Lifestyle Vault" is not one hub there — it contains NINE distinct sub-hubs, several with their own multi-level sub-trees: Family Hub · Spirituality Hub · Relationships Hub · Body & Health Hub · Mind & Identity Hub · Self-Expression Hub · Nourishment Hub · Adventures Hub · Personal Inventory. The planned architecture treats Lifestyle Vault as a single bounded context. That is a real discrepancy: either the app absorbs nine sub-hubs as sections of one context, or the roster grows from 4 bounded contexts to 12.

**Decision drivers.** The no-sibling-reads rule means every bounded context boundary is a wall that costs discipline to maintain · the nine sub-hubs already share the same spine tables in the source (Projects, Goals, Resources, Missions all fan out to them via one `Hub` multi-select) · solo builder in short sessions — every extra context multiplies hub-private tables and screens · v1 has one user.

**Considered options.** 1. Split Lifestyle Vault into nine bounded contexts. 2. Keep it as one bounded context with nine sections.

**Decision.** **Keep it as ONE bounded context with nine sections.** The nine sub-hubs become navigation sections and an `area` / section attribute inside the Lifestyle Vault context, not separate contexts with private tables and their own boundaries.

**Consequences.**
*   👍 The hub roster stays at 1 platform surface + 4 bounded contexts. Hub-private table count stays manageable. The nine sections already share spine tables, so nothing is being forced together that was truly separate. One set of screens to build, one boundary to police.
*   👎 Lifestyle Vault becomes by far the largest context — it carries recipes, the four food encyclopedias, inventory, workouts, health logs, the tracker stack, kids, spiritual and intimacy logs, adventures, media, and wishlist. It will be the hardest context to keep coherent and the most likely to need splitting later.
*   ⚖️ Watch / revisit trigger: split it if any one section grows its own private tables that no sibling section reads, or if a commercial multi-tenant release makes a section independently sellable. Revisit at the Phase 5 gate.

**Validation.** The Lifestyle Vault context ships with its sections sharing the spine and no cross-section private-table reads. If a section starts reaching into another section's tables, this ADR is being violated and the split question reopens.

#### ADR-0009: Today is consequence-first

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-09-07 |
| Deciders | Omegea Hunter |
| Tags | product, information-architecture, ux |

**Context and problem statement.** Today is the screen the kill criterion measures — the 6am one-tap loop. `UJGFREE-5913` (2026-08-26) made the app a public paid product with Omegea as user zero, so Today has to hold up for someone whose day is not shaped like hers. The question is what the screen leads with, because whatever is at the top is what the app claims the day is about.

**Decision drivers.** A phone is one column, so the eleven proven cockpit surfaces have to be RANKED, not tiled (4.1 §1.6) · the screen has to answer one question at 6am — what breaks if I skip today · a user with a light calendar must not be told their day is empty · anything that does not lead to a doable next step ranks below something that does.

**Considered options.** 1. Time-first — order by clock time, calendar at the top. 2. Ritual-first — open with a check-in, affirmation, or intention. 3. Static single card — one hard-picked next thing. 4. Consequence-first.

**Decision.** **CONSEQUENCE-FIRST.** The screen leads with what breaks if it is skipped: overdue first, then due-today, ranked by cost of missing rather than by time of day. Calendar context sits BELOW the ranked block, as context for the ranking rather than as the ranking itself.

**Alternatives rejected, and why.**
*   👎 **Time-first — rejected.** A day with two calendar entries renders as an empty screen even when six things are overdue. The screen would lie about the weight of the day, and it would lie hardest on exactly the days that need it most.
*   👎 **Ritual-first — rejected.** Opening with a check-in or an affirmation turns the screen into a ceremony. Ceremony is the first thing dropped under stress, and the loop dies with it.
*   👎 **Static single card — rejected.** One hard-picked next thing collapses trust the moment the pick is wrong, and nothing else is reachable from a wrong pick. See ADR-0010 for why a SEQUENCE is not the same object as a static card.

**Consequences.**
*   👍 The screen answers the only question that matters at 6am. A light-calendar day still reads honestly.
*   👍 The ranking rule is portable — the same cost-of-missing order drives notifications and rollups later.
*   👎 KNOWN FAILURE MODE, AND IT MUST BE DESIGNED AGAINST: an unbounded overdue list is a guilt list, and people stop opening guilt lists. Consequence-first without a bound is the fastest way to build a screen nobody opens.
*   ⚖️ Revisit if the capped block plus a real cleared state still produces avoidance in the beta.

**Required mitigation — not optional, ships with the screen.**

1. **Cap the overdue block** to a small fixed number of items with a "+N more" affordance. The rest is reachable, but it does not greet the user.
2. **Give it a genuine cleared state.** Not an empty list — a real, designed, unmistakable "you are clear" state. An empty list reads as a loading failure or as a screen that gave up; a cleared state reads as a win, and the win is the reason to open the app again tomorrow.

**Validation.** Beta instrumentation: days opened versus days skipped, and whether skipped days correlate with overdue count. A rising overdue count paired with falling opens is this ADR's failure mode firing, and it reopens the decision.

#### ADR-0010: One question, one screen — with an escape hatch

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-09-07 |
| Deciders | Omegea Hunter |
| Tags | product, interaction-model, accessibility, information-architecture |
| Scope | Product-wide — this is a screen composition rule, not a screen |

**Context and problem statement.** ADR-0009 settled what Today leads with. It did not settle how much of the day arrives at once. The default assumption in every planning doc up to this point was a dense scannable screen — the source system's three-column cockpit compressed into one column. That assumption was never argued for; it was inherited from the desktop layout the app is replacing. This ADR argues the question and reframes the product, because the answer applies to Today, capture, journal, and onboarding alike.

**Decision drivers.** The design is neurodivergent-first, and the primary cost being designed against is executive-function load, not screen count · a screen holding twelve decisions asks the user to choose which decision to make before making any of them, which is the expensive part · the app must survive being opened at 6am by someone with no momentum · a public paid product means the model has to hold for users other than the owner.

**Considered options.** 1. Dense scannable screens everywhere (the inherited default). 2. Static single card. 3. Sequential — one decision per screen — with no escape hatch. 4. Sequential with a persistent escape hatch.

**Decision.** **ONE QUESTION, ONE SCREEN. EVERYWHERE. WITH AN ESCAPE HATCH.**

Today, capture, journal, and onboarding are all SEQUENTIAL — one decision per screen. A screen carries one question, the context needed to answer it, and its actions. Nothing else. A persistent "show all" affordance sits on every sequential flow and drops the user into a scannable list for the mornings when the whole shape of the day is what is needed.

**How this composes with ADR-0009 — state this plainly, because a future session will otherwise treat them as competing.**

| Decision | What it governs |
| ---| --- |
| ADR-0009 consequence-first | THE ORDER — which thing is asked about first, ranked by cost of missing |
| ADR-0010 one question, one screen | THE DELIVERY — how many things arrive at once, which is one |

They are orthogonal and they compose. Consequence-first ranks the queue; one-question-one-screen serves the queue one item at a time. Neither one implies the other, and changing one does not reopen the other.

**Why a sequence is not the static single card rejected in ADR-0009.** A static card is TERMINAL — it makes one pick, and a wrong pick strands the user with no path to the thing they actually needed. A sequence is TRAVERSABLE — the user still reaches everything, in a defensible order, and can abandon the order at any point through the escape hatch. The rejected option failed on reachability, not on sparseness. Sparseness was never the problem.

**Alternatives rejected, and why.**
*   👎 **Dense scannable screens everywhere — rejected as the DEFAULT.** This is exactly what the escape hatch provides on demand, which is the point: as an on-demand view it is a tool, as the default it re-imposes the load the whole design exists to remove.
*   👎 **Static single card — rejected**, per ADR-0009: a wrong pick collapses trust and strands the user.
*   👎 **Sequential with no escape hatch — rejected.** It fails structure-oriented users completely and it makes the whole-day-shape morning impossible. Without the hatch this decision would be a worse product for half its stated audience.

**Rationale.** Reducing what is on screen lowers executive-function load. A screen with one question has exactly one decision on it, and the meta-decision — which of these twelve things do I deal with first — has already been made by the ranking. That meta-decision is the one that costs the most and gets paid every single morning.

**Honest caveat, recorded deliberately.** NEURODIVERGENT IS NOT ONE SET OF NEEDS. Some people orient by seeing whole structure, and a one-thing-at-a-time flow feels to them like being led through their own day blindfolded. That is precisely why the escape hatch is not a convenience feature and not a v2 nicety — it is the accommodation for the other half of the audience, and it ships with the first sequential flow or the flow does not ship.

**Second honest caveat.** "Built for neurodivergent people" is a CLAIM. Right now it has been tested on exactly one person, who is also the owner and the person who made the decision. It needs testing with people other than the owner before it goes into marketing copy or the store listing.

**Consequences.**
*   👍 A screen composition rule for the whole product rather than one screen. Every new surface now has to answer "what is the one question here," which is a useful forcing function on scope.
*   👍 Onboarding, capture, and journal get the same treatment for free instead of each being designed from scratch.
*   👎 More screens, more transition and progress state to build and test. A sequence of ten items is more taps than a list of ten items, and for a user who is fast and oriented that is pure cost.
*   👎 Every flow now needs a designed escape hatch, a progress indicator, and a defined resume point. That is a per-flow tax, paid forever.
*   ⚖️ Revisit trigger: if beta users LIVE in the escape hatch — if "show all" becomes the default path rather than the exception — then the sequence is the wrong default and this ADR is superseded, not patched.

**Validation.** Instrument escape-hatch usage rate per flow, and completion rate of sequential flows versus abandonment mid-sequence. Both numbers are read at the beta gate. Screen-level implications land in Information Architecture (4.1) §7 and Wireframes (4.2).

#### ADR-0011: Beta scope is Actions + Journal

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-09-07 |
| Deciders | Omegea Hunter |
| Tags | product, scope, release |

**Context and problem statement.** `UJGFREE-5913` made this a public paid product with a kill criterion attached: does the daily loop hold. A beta that ships everything cannot answer that question in any reasonable time, and a beta that ships too little gives the user no reason to come back.

**Decision drivers.** The beta exists to measure ONE thing — whether the loop holds daily · the two largest schema surfaces, money and calendar, contribute nothing to that measurement · a user needs something to open the app for on a day with no tasks.

**Considered options.** 1. Actions only. 2. Actions + Journal. 3. Actions + Money. 4. Full spine.

**Decision.** **ACTIONS + JOURNAL.**

IN: quick capture · Today (consequence-ranked per ADR-0009, sequential per ADR-0010) · complete and undo · areas · entities · the daily journal entry · email OTP auth.

OUT FOR NOW: money · calendar · academic · charts · offline writes.

**Alternatives rejected, and why.**
*   👎 **Actions only — rejected.** Once the list is clear there is nothing to come back for. The journal is the reason to open the app on a day with no tasks, and days with no tasks are exactly the days a habit dies.
*   👎 **Actions + Money — rejected.** Money is the largest schema surface in the plan and it does not test the loop. It would double the build to measure the same thing.
*   👎 **Full spine — rejected.** Delays the measurement by months and makes any negative result unreadable, because a failed loop could be blamed on any of nine surfaces.

**Consequences.**
*   👍 The smallest scope that still tests the thing being measured, and it is honestly sellable as a beta rather than as a demo.
*   👎 INCLUDING THE JOURNAL PULLS FAILURE-CHAIN ITEM FC-3 (sensitive module bypass) INTO THE BETA. The biometric gate stops being a Phase 4 nicety and becomes beta work. That cost is accepted and discharged in ADR-0013.
*   👎 Areas and entities ship with no money or calendar rows to scope, so part of the tenancy model is carried without being exercised.
*   ⚖️ Revisit at the beta gate. Money is first in the queue after the loop is proven.

**Validation.** The beta ships with every listed IN item working end to end and no OUT item half-present in the UI. A greyed-out money tab is a scope leak, not a roadmap hint.

#### ADR-0012: Online-only for the beta

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-09-07 |
| Deciders | Omegea Hunter |
| Tags | architecture, data, release |
| Relates to | ADR-0001 (offline was a founding reason for going native) |

**Context and problem statement.** Genuine offline capture was one of the reasons the app went native at all (ADR-0001). Building it properly means a sync layer and a conflict-resolution policy, which is the single largest piece of engineering in the plan. The beta needs to measure the loop, not the sync layer.

**Considered options.** 1. Full offline-first now with local storage and sync. 2. Optimistic local queue with no durable storage. 3. Online-only with a clear error and a retry.

**Decision.** **ONLINE-ONLY FOR THE BETA.** Writes require a connection. A failed write shows a clear error and a retry — not a silent failure, not a fake success. `expo-sqlite` and full offline-first are DEFERRED. Failure-chain item FC-4 (offline write conflict) is NOT exercised in the beta, and that is stated so nobody later assumes it was.

**Alternatives rejected, and why.**
*   👎 **Full offline-first now — rejected.** It is the largest build in the plan and it would delay the very measurement it is supposed to protect. Offline matters most once the loop is proven worth protecting.
*   👎 **Optimistic local queue with no durable storage — rejected.** All of the complexity of offline with none of the guarantees. A queue that dies when the app is killed is a data-loss bug wearing a feature's clothes.

**Consequences.**
*   👍 The beta ships months earlier and the data layer stays simple enough to reason about alone.
*   👎 A user on flaky wifi at 6am hits a failure in the exact moment being measured.
*   ⚖️ Offline-first returns as a scoped project once the loop is proven, and FC-4 is exercised then. Until it is, no doc may describe the app as offline-capable.

**Required mitigation — not optional, ships with the beta.**

EVERY FAILED WRITE IS LOGGED LOCALLY WITH A TIMESTAMP.

The kill criterion measures daily friction. A write that failed on bad wifi is NOT a design failure, but in drop-off data a network failure and an "this app is annoying" failure look identical. Without that local log the beta result cannot be read honestly — a run of bad connectivity would read as a rejected design, and the app would be killed for the wrong reason. The log is the instrument that separates the two.

**Validation.** At the beta gate, failed-write timestamps are cross-referenced against skipped days before any conclusion is drawn about the loop.

#### ADR-0013: Biometric gate on the journal only

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-09-07 |
| Deciders | Omegea Hunter |
| Tags | security, ux, release |
| Relates to | ADR-0011 (the journal in beta scope is what forces this) |

**Context and problem statement.** ADR-0011 put the daily journal in the beta, which pulls FC-3 (sensitive module bypass) forward. The app therefore needs a gate. The open question is what the gate sits in front of, and every extra thing behind it is friction on the loop being measured.

**Decision drivers.** The kill criterion measures a 6am ONE-TAP loop, so anything in front of that loop contaminates the measurement · FC-3 needs to be exercised on real routes, not on a placeholder · the journal is the only genuinely sensitive content in beta scope.

**Considered options.** 1. Whole-app gate at launch. 2. No gate in beta. 3. Gate on the journal plus at-rest encryption of entries. 4. Gate on the journal only.

**Decision.** **BIOMETRIC GATE ON THE JOURNAL ONLY.**

The app opens freely. Today, capture, and complete are instant. Face ID / fingerprint is required only to ENTER OR READ journal entries. Implemented with `expo-local-authentication`. The gate renders at `z-gate` (z-index 900, already in the token set) above everything, so nothing can paint over it or slide out from under it. GATE STATE MUST NOT PERSIST ACROSS BACKGROUNDING — re-authenticate on return, every time.

**Alternatives rejected, and why.**
*   👎 **Whole-app launch gate — rejected.** It puts a gate directly in front of the interaction being measured. A one-tap loop becomes a two-step loop, and every drop-off number afterwards is unreadable.
*   👎 **No gate in beta — rejected.** It leaves FC-3 unexercised and turns the route guard into a retrofit. Route guards retrofitted after the routes already exist are precisely where bypasses live.
*   👎 **Gate plus at-rest encryption — rejected.** Encrypting entry bodies breaks server-side search and any future sync, and it is disproportionate for content nobody else can currently reach. Revisit it when the app holds a second person's journal, not before.

**Consequences.**
*   👍 FC-3 is exercised at real cost on a real route, and the measured loop stays one tap.
*   👍 The gate pattern is built once and is reusable for Spiritual Practice / Intimacy in the Lifestyle Vault later.
*   👎 The journal carries a friction step by design, and re-authenticating after every backgrounding will annoy the user who checks a text mid-entry. That is the intended trade.
*   ⚖️ Revisit when the app holds anyone else's data — multi-profile or the commercial release — at which point encryption at rest is argued on its own merits.

**Validation.** FC-3 test: deep-link straight to a journal route without authenticating. The gate must render, and no entry content may reach the screen or the cache. Backgrounding and returning must re-prompt.

#### ADR-0014: Vercel is the compliance surface first

| Field | Value |
| ---| --- |
| Status | Accepted |
| Date | 2026-09-07 |
| Deciders | Omegea Hunter |
| Tags | infra, legal, release, repo |

**Context and problem statement.** `UJGFREE-5913` made this a public paid product, which means store submission. Google mandates a PUBLICLY ACCESSIBLE WEB URL for account-deletion requests, separate from the in-app deletion path. Both stores require privacy policy and terms links in store metadata AND inside the app. None of that can live only inside an Expo binary, so a web surface is a submission requirement rather than a marketing choice.

**Considered options.** 1. No web surface. 2. Marketing site first, compliance pages inside it. 3. Compliance pages on [urbanjunglegoddess.com](http://urbanjunglegoddess.com) in Wix. 4. A minimal Next.js compliance app on Vercel.

**Decision.** **A SMALL NEXT.JS APP ON VERCEL CARRYING ONLY WHAT THE STORES REQUIRE** — a public account-deletion request page, the privacy policy, and the terms of service. MARKETING AND WAITLIST ARE EXPLICITLY DEFERRED.

The repo becomes a monorepo:

| Path | Contents |
| ---| --- |
| `apps/mobile` | The Expo app |
| `apps/web` | The Next.js compliance app on Vercel |
| `packages/` | Shared types and design tokens |

**Alternatives rejected, and why.**
*   👎 **No web surface — rejected.** Store rejection. The public deletion URL is not optional and cannot be satisfied in-app.
*   👎 **Marketing site first — rejected.** Marketing pages unblock nothing and cost real time. This is a compliance surface that will later grow marketing, not a marketing site that happens to carry policies.
*   👎 **Policy pages on** [**urbanjunglegoddess.com**](http://urbanjunglegoddess.com) **in Wix — rejected.** It mixes a client-facing consultancy brand with a product's legal surface, and it puts store compliance behind a site edit in a different tool. The compliance pages have to version with the app that they describe.

**Consequences.**
*   👍 Store submission is unblocked, and policies version alongside the app they describe.
*   👍 Shared types and tokens stop drifting between the two apps once `packages/` exists.
*   👎 A monorepo and a second deploy target before there is a marketing reason for either. Build tooling gets more complicated on day one.
*   ⚖️ Marketing and the waitlist land in the same `apps/web` later at near-zero marginal cost — that is the payoff for taking the monorepo cost now.

**Validation.** The deletion page is reachable at a public URL with no auth, the URL is entered in both store listings, and the same policy and terms links resolve from inside the app.
