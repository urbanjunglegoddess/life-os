### 1\. Overview

Postgres, hosted by Supabase. The model below is the SPINE — a small set of general tables that absorb the ~35 databases of the Notion Command Center. The source system's core problem is that it repeats one shape (a thing with a status and a date) across a dozen near-duplicate tables. The spine collapses those into `actions`, `events`, `days`, and `notes`, and leaves genuinely domain-specific data in hub-private tables.

| Property | Value |
| ---| --- |
| Engine | Postgres, hosted by Supabase |
| Hosting | Managed — separate projects for dev / staging / prod |
| Time zone convention | UTC in storage; local display in client |
| Naming convention | `snake_case`, plural table names, `*_logs` for time-series, `v_*` for views |
| Key strategy | Surrogate `uuid` primary keys |

#### Universal column conventions

Every table has:

| Column | Type | Notes |
| ---| ---| --- |
| `id` | uuid | Primary key |
| `tenant_id` | uuid | FK → `tenants`. Present on EVERY row, no exceptions. This is the RLS wall. |
| `profile_id` | uuid | FK → `profiles`, where the row belongs to a person |
| `entity_id` | uuid | FK → `entities`, where the row belongs to a set of business books |
| `created_at` | timestamptz | Default `now()` |
| `updated_at` | timestamptz | Default `now()` |

Only distinctive columns are listed below.

**`tenants`** — name, plan, created\_at. One row per account. Isolates Omegea from any future Freelance Life OS customer (ADR-0004).
**`profiles`** — tenant\_id, auth\_user\_id, display\_name, role (owner/child), settings jsonb.
**`entities`** — tenant\_id, name (Empire / UJG / JMR / Personal), type. FK target for every `entity_id` column.

### 2\. The Spine

Every hub inherits these through the shared data-access layer. Every row carries `tenant_id`, plus `profile_id` or `entity_id` where relevant.

#### 2.1 `actions` — the universal unit

Everything that can be done, planned, or checked off is one row here.

| Column | Notes |
| ---| --- |
| `id` | uuid PK |
| `tenant_id`, `profile_id` | Tenancy + ownership |
| `title` | Short label |
| `notes` | Long form |
| `kind` | ENUM — task · project · goal · habit · routine\_step · sop · opportunity |
| `status` | ONE status field. The source keeps two — Status and Assignment Status — and they collapse here. |
| `priority` | ONE normalized scale — see MIGRATION DEFECT 1 |
| `area_id` | FK → `areas` |
| `hub_id` | FK → `hubs` |
| `due_at` | ONE date field. The source keeps Date and Dates, and they collapse here. |
| `scheduled_for` | The day it is meant to be worked, distinct from when it is due |
| `parent_id` | Self-FK. Project → sub-project → task is ONE relation, not three tables. |
| `source_kind` + `source_id` | Polymorphic pointer back to the record that spawned it |
| `deep_link` | Do-now target |
| `completed_at` | Null until done |

Children of `actions`:

| Table | Carries |
| ---| --- |
| `action_dependencies` | action\_id, depends\_on\_action\_id, relation — blocks / blocked\_by |
| `action_templates` | Reusable action definitions — the SOP and routine bodies |
| `recurrence` | template\_id, cadence, next\_due, last\_done. Replaces the hand-maintained cadence columns in the source. |
| `action_logs` | action\_id, occurred\_on, done. ONE row per occurrence. This is where habit history finally exists. |

#### 2.2 `events` — the time layer

| Column | Notes |
| ---| --- |
| `tenant_id`, `profile_id`, `entity_id` | Tenancy + ownership + books |
| `title` | Short label |
| `kind` | ENUM — work\_session · focus\_block · routine\_run · appointment · trip · meal\_slot · bill\_due · day |
| `scheduled_start`, `scheduled_end` | PLANNED |
| `actual_start`, `actual_end` | ACTUAL. Planned-vs-actual is a first-class property of the time layer, not a per-table accident. |
| `duration_min` | GENERATED from actual\_start / actual\_end |
| `action_id` | The action this occurrence belongs to |
| `template_id` | FK → `event_templates` |
| `area_id` | FK → `areas` |

Child: **`event_templates`** — archetypes that GENERATE events for a date. Pomodoro block types, break types, and full day schedules live here. A template has no timestamp.

#### 2.3 `days` — one row per calendar day

| Column | Notes |
| ---| --- |
| `date` | UNIQUE per profile |
| `day_type_id` | FK → `day_types` |
| `mood` | array |
| `energy`, `motivation`, `day_rating` | Scalars |
| `notes` | Short daily note. Long form goes to `notes`. |
| `cycle_phase` | Phase label |

Lookup: **`day_types`** — see the seed table in §8 and MIGRATION DEFECT 3.

#### 2.4 `notes`

| Column | Notes |
| ---| --- |
| `date` | Date the note belongs to |
| `body` | Long form |
| `kind` | ENUM — journal · brain\_dump · dream · reflection |
| `tags` | array |

Child: **`note_links`** — note\_id, entity\_kind, entity\_id. ONE polymorphic link table replaces per-module note relations.

#### 2.5 Money

| Table | Distinctive columns |
| ---| --- |
| `accounts` | name, type, institution, last4, is\_synced |
| `transactions` | account\_id, entity\_id, type, amount, category, occurred\_on |
| `recurring_rules` | label, amount, cadence, next\_due — spawns actions and events |
| `budgets` | period, category, amount |
| `buckets` | Allocation buckets |
| `bucket_rules` | bucket\_id, effective\_from, sprint\_id, pct — allocation percentages are versioned, never overwritten |
| `mileage_rates` | tax\_year, rate\_per\_mile. The rate is DATA, not a constant inside a formula. |

#### 2.6 The rest of the spine

| Table | Carries |
| ---| --- |
| `people` | Contacts. Collapses THREE separate client/contact tables in the source. |
| `goals` | start\_value, end\_value, target\_date — the measurable detail behind an `actions` row with kind=goal |
| `missions` | The planning half of a mission. Occurrences live in `events`. |
| `areas` | Self · Home · Money · Business · Academic · Kids · Spirit |
| `hubs` | The hub taxonomy — ONE lookup, replacing five drifted multi-select copies |
| `resources` | The generic library table |
| `courses` | A real course entity. The source has none. |
| `assignments` | course\_id, title, due\_at, status — with a real FK to a course, which the source also lacks |

### 3\. Source-to-Target Migration Map

| Notion source | Becomes | Note |
| ---| ---| --- |
| Tasks | `actions` (kind=task) | Status + Assignment Status collapse to ONE. Date + Dates collapse to ONE. |
| Projects (canonical) | `actions` (kind=project) | Parent/sub is the same self-relation, not a second table |
| Projects (Income Command Center) | Merged into `actions` | A SECOND, SEPARATE database. It has no relation to the canonical Projects table at all. |
| Goals | `actions` (kind=goal) + `goals` detail | Measurable fields split out |
| Sprints | A period on `events` | Thin and near-abandoned — 7 properties, ONE outbound relation. It groups Tasks by date range and has no substance of its own. |
| Missions | `actions` (planning half) + `events` (occurrence half) | Missions is the ONLY Notion table doing planned-vs-actual properly. Generalizing that lets its two date columns collapse. |
| SOP Library | `action_templates` + `recurrence` | Its Cadence + Next Due + Last Done is maintained BY HAND with no formula. Clearest recurrence-rule table in the source. |
| `Clients.Next Action` + `Clients.Next Action Date` | `actions` | An action hidden as two columns on a client row |
| Checklists (10 pages), Morning / Afternoon / Evening Routine, Workday Startup | `actions` + `action_templates` | ~300+ actions currently trapped as markdown checkboxes with ZERO completion history |
| Daily Tracker's ~70 boolean columns | `actions` (kind=habit) + `action_logs` rows | THE SINGLE BIGGEST STRUCTURAL FIX in the migration |
| Timesheet | `events` (kind=work\_session) + money columns | The only source table with a real start/end |
| ⏱️ Blocks | `event_templates` | NOT events. A catalogue of ~30 archetypes with NO timestamp. Nothing in Notion records a Pomodoro round actually happening. |
| Day Schedules (20 day types, hour-by-hour tables) | `event_templates` | Schedule templates that generate events for a date |
| Journal + Daily Tracker | ONE `days` table | Both are one-row-per-day, joined 1:1, with Daily Tracker rolling up Day Type and Energy Level from Journal |
| Journal bodies, brain dump, dream journal, reflections | `notes` | One table, one polymorphic link |
| Reports (19 formulas) | NOT a table — ONE materialized view over a date range | Reports itself becomes a period definition: start, end, scope |
| Company Ledger | `entities` | The books each row belongs to |
| Clients + CRM + Missions' smuggled contact fields | `people` | Three sources, one table |
| Resources | `resources` + `courses` + `assignments` | ELEVEN "academic databases" are all filtered views of this ONE generic table, separated by a Type select. No Course entity, no Assignment entity, no grade, no credit hours, no term, and no course→assignment FK exists today. |
| Invoices, Pipeline | Control Room hub-private tables | Stay inside the hub boundary |
| Recipe Book + Herbal / Fruit / Vegetable / Pantry encyclopedias | Lifestyle Vault hub-private | A near-complete two-way mesh and the HEALTHIEST cluster in the entire source system. Port it close to as-is. |
| Inventory & Assets | `inventory_items` | Quantity and Restock Level are typed TEXT today and can never be summed |
| Wishlist, Workouts, Media, Content Calendar, Quotes / Affirmation | Hub-private tables | Domain-specific, not spine |
| Hub multi-select | `hubs` lookup + FK | Duplicated VERBATIM on FIVE databases and already drifted — Resources has a 10th option the others lack |

#### 3.1 Computed values — what becomes what

**GENERATED COLUMNS** — stored, deterministic from other columns in the row:

| Value | Derived from |
| ---| --- |
| `events.duration_min` | actual\_start / actual\_end |
| Work-session `total_pay`, `net_cash`, `$/delivery`, `$/hr_effective` | base\_pay, tips, deliveries, miles, expenses |
| Mileage deduction | JOINED to `mileage_rates` by tax year — NOT hardcoded |

**VIEWS ONLY** — `now()`\-dependent, therefore never stored:

*   Goals "Days until due"
*   Missions "Date Countdown" and "Days passed" — the SAME signed integer split into two positive-only columns
*   All 19 Reports formulas
*   Goal progress

**DELETED OUTRIGHT:**

| Dropped | Why |
| ---| --- |
| `Tasks.Category`, `Missions.Associated with` | Rollups copying a parent's category — a JOIN in SQL |
| `Projects.Total Tasks` | A count written as a formula |
| `Tasks.Schedule Day`, `Projects.Schedule Day` | The same expression duplicated in two tables |
| Timesheet "Hours & Mins" | A display string stored as a column |
| Quotes "Randomnizer" | A fake random-sort column. Postgres has ORDER BY random(). |
| Daily Tracker Day Type + Energy Level rollups | They vanish when Journal and Daily Tracker merge into `days` |

#### 3.3 Retired: the `cms_*` collections

**Payload CMS was dropped (ADR-0003.)** The former Payload-owned collections — recipes, recipe ingredients, affirmations, media, resources, digital asset catalog, content templates — are ordinary app tables, tenant-scoped like everything else, edited through in-app editors with Supabase Studio for bulk work. The `cms_` prefix is retired, and the one-writer-per-table rule retired with it. The rule that replaces it is the hub-boundary rule: **no hub reaches into a sibling hub's tables.**

| Index | Table | Column(s) | Rationale |
| ---| ---| ---| --- |
| btree | every table | `tenant_id` | On every query path — the RLS predicate |
| btree | `actions` | (due\_at, completed\_at) | Drives the Today snapshot |
| btree | `actions` | (kind, status) | Every hub list view filters on these |
| btree | `actions` | (parent\_id) | Project → sub-project → task traversal |
| btree | `actions` | (source\_kind, source\_id) | Resolving an action back to the record that spawned it |
| Unique | `action_logs` | (action\_id, occurred\_on) | One log per action per day; makes the reset job idempotent |
| Unique | `days` | (profile\_id, date) | One day row per profile |
| btree | `events` | (scheduled\_start) | Drives the schedule surface |
| btree | `events` | (kind, actual\_start) | Work-session and focus reporting |
| btree | `note_links` | (entity\_kind, entity\_id) | Polymorphic lookup from any record to its notes |
| btree | `assignments` | (course\_id, due\_at) | Assignments due, by course |
| btree | `transactions` | (occurred\_on, entity\_id) | Monthly in/out and entity rollups |
| btree | `bucket_rules` | (bucket\_id, effective\_from) | Resolving the allocation rule in force on a date |

### 5\. Partitioning & Sharding

None in v1. Single-tenant data volumes do not justify it. `action_logs` is the only table with meaningful row growth, and it is bounded by actions × days. Revisit if the commercial multi-tenant release happens (`FUTURE-STATE` Phase 7).

### 6\. Migration Strategy

*   **Tool:** plain SQL migrations, applied through Supabase.
*   **Location:** `/db`
*   **Naming / versioning:** numbered and **append-only** — `0001_init.sql`, `0002_spine.sql`, and so on.
*   **Golden rule:** never edit an applied migration; add a new one.
*   **Sequencing rule:** the spine ships first. Hub-private tables follow, and each hub's first build session ships its migration **before any screen**.
*   **Tenancy rule:** the migration that creates a table creates its `tenant_id` column **and** its RLS policy. Never in two steps.
*   **Idempotency:** migrations and all scheduled jobs must be safe to run twice.
*   **Formula rule:** no computed column ships until its source expression has been read in the Notion UI and classified per §3.1. A generated column written from a guess is worse than no column.

| Change type | Safe approach | Rollback |
| ---| ---| --- |
| Add column | Nullable or defaulted, then backfill | New migration dropping it |
| Drop column | Only after code stops using it | Restore from backup / re-add |
| Rename column | Add new → dual-write → migrate → drop old | New migration reversing the step reached |
| Add index | Create concurrently | Drop index |
| Add generated column | Additive; recompute is automatic | Drop column |
| Data backfill | Batched, idempotent script | Re-run against a copy |
| Collapse N source tables into one | Import script writes to the spine table with `source_kind` + `source_id` preserved | Re-run that source's import; the source pointer scopes the delete and makes every row traceable |

### 7\. Rollback & Recovery

Migrations are forward-only. Rollback is by new migration, never by editing history. App-level rollback is **EAS Update revert + safe Supabase migration down**.

| Scenario | Detection | Response |
| ---| ---| --- |
| Migration fails partway | Apply error on run | Fix forward in a new numbered migration; the failed file is never edited |
| Migration succeeds but breaks the app | Real-device pass fails | Corrective migration + EAS Update revert; the slice is not done until the device pass passes |
| Notion migration row-count mismatch | Verified counts before cutover | Do not cut over; Notion stays live until counts reconcile |
| A collapsed-table import lands wrong | Row counts per `source_kind` do not match the source database | Re-run that one source's import; `source_kind` scopes the delete |
| A table found without RLS | Failure-chain test 1 | Treat as an incident, not a bug — fix before any release |

**Dev / Staging / Prod are separate Supabase projects** paired with EAS channels. Schema changes flow dev → staging → prod, applied from `/db` in order. See Environment Strategy (5.12).
