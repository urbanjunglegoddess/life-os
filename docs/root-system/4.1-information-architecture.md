### 2\. Overview & Scope

The platform is briefed once in the Application Brief. This map names **the shared spine every hub inherits**, the hub roster, and which hubs are bounded contexts versus platform surfaces.

*   **Primary users:** Omegea (owner, tenant 1, user zero) · child profiles (Demarze, Belle — scoped) · paying public users — the app ships as a public paid product per `UJGFREE-5913` (2026-08-26) · `FUTURE-STATE` commercial Freelance Life OS tenants.
*   **Top user goals this IA must support:** see what breaks if today is skipped and act on it · capture anything in one or two taps · move money, time, work, wellness, home, academics, and family through one cockpit.
*   **Design principles / constraints:** mobile-first · action-first (every surface should lead somewhere doable) · **one question, one screen, with an escape hatch** (ADR-0010) · **consequence-first ordering** (ADR-0009) · no hub reaches into a sibling's data · WCAG 2.1 AA · every state (loading / empty / error / cleared).

### 3\. Architecture Pattern

**Shared-kernel, not distributed services.** One Postgres, one codebase.

The spine is an inherited platform layer all hubs use through a shared data-access layer. Each bounded-context hub owns its own private tables. **No hub reaches into a sibling hub's tables** — cross-hub needs go through the spine or an explicit interface.

> This is how _independent but connected_ stays honest inside a single app instead of rotting into a distributed monolith.

#### 7.1 The sequential interaction model — one question, one screen

Decided 2026-09-07, recorded as **ADR-0010 (5.3)**. This is a PRODUCT-WIDE COMPOSITION RULE, not a behavior of one screen. Today, quick capture, the daily journal entry, and onboarding are all sequential — one decision per screen.

**The two decisions compose and they are not the same decision.** Consequence-first (ADR-0009) decides THE ORDER — which thing gets asked about first. One question, one screen (ADR-0010) decides THE DELIVERY — how many things arrive at once, which is one. Changing one does not reopen the other.

**What one screen contains — and nothing else:**

| Slot | Contents | Rule |
| ---| ---| --- |
| The question | One decision | Exactly one. If a screen carries two decisions, it is two screens |
| The context | The minimum needed to answer it — due date, area, source record, do-now link | Context makes the question answerable; it must never become a second question |
| The actions | The responses to that question | Two to four, and one of them is always a defer |
| Progress | Position in a bounded queue, such as 3 of 7 | Bounded and honest; never an open-ended scroll |
| Escape hatch | Show all | Same position on every screen of every flow |

**How a flow is structured:**

1. **Build the queue.** Ordering rules are per-flow. Today's is consequence-first per ADR-0009.
2. **Bound the queue and state its size up front.** The user has to know how long this is before starting it. An unstated length is the same anxiety as an unbounded list.
3. **Serve one item per screen**, in queue order.
4. **Every screen offers a response and a way out** — an answer, a defer, and the escape hatch.
5. **End on a designed terminal state.** The cleared state, never a blank screen.

**Progress and resume.** Progress is shown as position in a bounded queue. Leaving mid-flow and returning resumes at the same position within the same day. **The queue does not reshuffle under the user mid-sequence** — a queue that re-ranks itself between two screens destroys the user's sense of how much is left, which is the one thing the progress indicator exists to protect.

**Why sequential rather than a dense scannable screen.** The design is neurodivergent-first, and the cost being designed against is executive-function load. A screen holding twelve decisions asks the user to choose WHICH decision to make before making any of them, and that meta-decision is the expensive one — it gets paid every single morning. Consequence-first ranking makes that choice once, up front, so the screen never asks it again.

**The honest caveat, recorded on purpose.** NEURODIVERGENT IS NOT ONE SET OF NEEDS. Some people orient by seeing whole structure, and a one-thing-at-a-time flow feels to them like being walked through their own day blindfolded. That is exactly why the escape hatch is not optional. And "built for neurodivergent people" is a claim currently tested on one person, who is also the owner — it needs testing with other people before it goes into marketing copy or a store listing.

#### 7.2 The escape hatch

**Where it lives.** Persistent, in the same position on every screen of every sequential flow — below the primary actions, out of the main tap path, reachable without scrolling. Position never changes between flows, because a hatch you have to hunt for is not a hatch.

**Label.** Show all. See §9 for the labeling rule.

**What it does.** Drops the current flow into a scannable list of the whole queue, in the same order the sequence would have served it. There is no second ordering to learn — the list is the sequence, flattened.

**Return path.** Tapping any item in the list opens that item's single-question screen and resumes the sequence from there. The hatch is a view, not an exit.

**Why it is not optional.** It is the accommodation for the half of the audience that orients by structure rather than by focus (§7.1). A sequential flow ships with an escape hatch or it does not ship.

#### 7.3 The Today flow

**Order — consequence-first, per ADR-0009 (5.3).**

1. **Overdue**, capped — ranked by cost of missing, not by clock time.
2. **Due today** — ranked by cost of missing, not by clock time.
3. **Calendar context** — sits BELOW the ranked block and never above it. `FUTURE-STATE`: calendar is out of beta scope per ADR-0011, so the beta Today flow has no calendar strip at all. It lands with the calendar phase.

**The overdue block is CAPPED.** A small fixed number of items with a plus-N-more affordance. The rest stays reachable through the hatch, but it does not greet the user. This is not a polish item — an unbounded overdue list is a guilt list, and people stop opening guilt lists, which kills the exact loop the beta is measuring. The cap number is Open Question 9.

**Per-card actions.** Each Today screen presents ONE item and three responses:

| Action | What it does |
| ---| --- |
| Do now | Follows the do-now deep link to where the item is actually completed, then returns to the sequence at the same position |
| Later | Defers the item to a chosen point and advances. It stays counted as DEFERRED, not as cleared — the count must not be gameable |
| Drop | Removes the item from today with a reason. Undo is available for the rest of the session |

**The cleared state.** Designed, not empty. It names what was cleared, shows whatever day context exists below, and offers capture as the next move. An empty list reads as a loading failure or as a screen that gave up; a cleared state reads as a win, and the win is the reason to open the app again tomorrow. **Every sequential flow needs one — Today's is the one that matters most.**

#### 7.4 Where lists still exist

Sequential is the default, not a ban on lists. A list is right when the user is SCANNING. A sequence is right when the user is DECIDING. If a surface asks for a series of decisions, it is a sequence.

| Surface | Why a list beats a sequence here |
| ---| --- |
| The escape hatch view — Show all | The user has explicitly asked for the whole shape of the queue |
| Search and results | Scanning IS the task |
| Areas and entities pickers | Choosing from a known set is one decision presented as a set, not many decisions |
| Journal history and archive | Browsing past entries is scanning, not deciding — behind the gate, per §6.2 |
| Settings | Reference, not a decision queue |

#### 9.1 Naming drift found in the source — must be settled before build

The crawl surfaced three naming failures. None of them is cosmetic; each one is a place where the same thing answers to different names depending on who is pointing at it.

**A. One table, four names.**

| Who is pointing at it | What it is called there |
| ---| --- |
| The table's own title | Missions |
| The table's own ID column | Experience ID |
| Projects | Events |
| Journal | Today's Missions |
| Tasks · Goals · Reports · Timesheet | Experiences |

PICK ONE NAME IN THE APP. The planned spine splits this table into **Actions** and **Events** anyway, so the naming cannot be inherited — it has to be decided deliberately, and the split has to be decided alongside it. Feeds: Database Schema (5.6) · Data Architecture (5.5).

**B. "Block" means three different things in one word.**

| Source meaning | Where it lives | App term |
| ---| ---| --- |
| A focus-session archetype | `⏱️ Blocks` database | `session_template` |
| A named time-of-day window | `Best Time Slot` on that same table | `time_window` |
| A dependency | `Blocked by` / `Blocking` on Tasks and Projects | `dependency` |

Three meanings, one word, one table carrying two of them. The app splits them into three named concepts and never uses the bare word "block" in UI copy.

**C. "Day type" is defined four times, incompatibly.**

Four separate definitions with four different vocabularies — 20, 21, 7, and 12 values respectively. There is no merge path that preserves all four. One canonical vocabulary gets defined in Database Schema (5.6) and everything else maps into it.

### 10\. Content Hierarchy

**The rule.** Whatever sits highest is what the app claims the moment is about. On a one-column phone, position IS the argument (§1.6) — three columns tile, one column ranks. Hierarchy is therefore decided once, product-wide, and every screen inherits it rather than re-arguing it.

**Screen-level hierarchy inside a sequential flow** — the slot order from §7.1, in priority order:

| Rank | Element | Why it sits here |
| ---| ---| --- |
| 1 | The question | The single decision the screen exists for |
| 2 | The context | Due date · area · source record · do-now link — only enough to answer, never a second question |
| 3 | The actions | Two to four responses, one of which is always a defer |
| 4 | Progress | Position in a bounded queue — reassurance, not content |
| 5 | Escape hatch | Always present, same position every time, out of the main tap path |

**Queue-level hierarchy on Today** — consequence-first per ADR-0009 (5.3): capped overdue, then due today, then calendar context below the ranked block, ending on the designed cleared state. Detail in §7.3.

**Where the eleven proven cockpit surfaces land.** §1.6 established the source cockpit as observed evidence rather than a guess. Ranking replaced tiling, so each surface now has one destination:

| Source cockpit surface | Where it lands in the app | In beta? |
| ---| ---| --- |
| Today | The Today flow, rank 1 | YES |
| Do Now | The do-now deep link carried on every Action | YES |
| Missions Today | Merged into the Today queue as Actions | YES |
| Routines Today | Templates / Routines spawn Actions into Today | NO |
| Active Projects | Productivity | NO |
| Meals Today | Lifestyle Vault | NO |
| Workout Today | Lifestyle Vault | NO |
| Money | Control Room | NO |
| Goals in Focus | Rollups on the Command Center | NO |
| Content | Control Room — marketing | NO |
| People to Contact | The spine's People / CRM | NO |
| Schedule — link out | The calendar phase | NO |

**Priority rule for anything new.** Rank by whether it leads to a doable next step. Anything that does not lead somewhere doable ranks below anything that does. Reports, charts, and rollups are the lowest tier by definition — they describe, they do not resolve. Feeds: Wireframes (4.2) · Design System (4.5).
