### 1\. Why This App Exists — The Four Structural Failures

The Life OS App replaces the Omegea Command Center, a Notion hub of roughly 35 databases. The crawl found four failures that are structural, not cosmetic. Everything in the model below exists to close one of them.

| # | Failure | What the source system actually does | What the app does instead |
| ---| ---| ---| --- |
| 1 | THE DAY IS SPLIT IN TWO | `Journal` and `Daily Tracker` are both one-row-per-calendar-day and joined 1:1. Daily Tracker ROLLS UP `Day Type` and `Energy Level` from Journal purely so the two can be seen together — a self-join dressed up as data | ONE `days` table. Two rollups die outright |
| 2 | ~70 HABITS ARE COLUMNS, NOT ROWS | Daily Tracker carries about 70 boolean columns — one per habit. Adding a habit is an ALTER TABLE | `action_logs` rows. Adding a habit is an INSERT |
| 3 | FORMULA CHAINS | Notion cannot reference a formula from a formula, so every column re-expands the whole tree. Timesheet runs Hours Worked → Total Pay → Net Cash → $/hr Effective, each re-expanded. Reports carries 19 formulas that are really 10 metrics split into positive/negative pairs — Met/Not Met, Completed/Missed, Attended/Not Attended | Generated columns for row-local math, views for cross-row aggregates. One metric, one home, signed values instead of mirrored pairs |
| 4 | ~300+ ACTIONS TRAPPED AS MARKDOWN | Every Checklist page, the Morning / Afternoon / Evening Routines, Workday Startup, and 20 Day Schedules are recurring actions living as prose checkboxes — zero completion history, zero queryability | All of it becomes `actions` plus `action_templates` plus `action_logs` |

### 2\. Overview & Principles

The Life OS App is **ONE RECORD, MANY VIEWS**. Hubs are lenses over a shared core, not silos. A task in quick-capture, a bill due in the ledger, and a study block in Academic HQ are the same kind of thing seen from different angles — Actions and Events on one shared spine.

Platform: mobile-first React Native / Expo on a single relational store, **Postgres on Supabase**. No document store, no graph store, no separate OLAP warehouse. Reporting is served from views and periodic snapshots inside the same database (§13).

Guiding principles:

*   **Shared kernel, not distributed services.** One Postgres, one codebase, one shared data-access layer.
*   **Three-layer multi-tenancy.** Tenant → profile → entity. `tenant_id` on every row without exception.
*   **Each datum has exactly one owner.** Spine entities belong to the platform layer; hub-private entities belong to that hub alone.
*   **No hub reaches into a sibling hub's tables.** Cross-hub needs go through the spine.
*   **Actions are the atomic unit.** Plans, goals, bills, routines and rituals all decompose into Actions; progress rolls up from completed Actions rather than being typed by hand.
*   **No duplicated formulas** — the anti-Notion rule (§14).

`PAUSED` — Payload CMS was DROPPED (ADR-0003). The former `cms_*` collections are ordinary tenant-scoped app tables edited through in-app editors, with Supabase Studio for bulk work.

### 4\. Conceptual Data Model

In plain language: **one household account (tenant) contains people (profiles) and businesses (entities). Everything a person does becomes an Action. Anything with a time becomes an Event. Every calendar day is one row. Money moves through a ledger. Ambitions live on a Goals ladder that only advances when Actions complete. Thoughts land in Notes. Every record carries a life Area, which is how the cockpit and the reports slice a whole life into views.** Hubs are the lenses — they add private detail (a recipe, a course, a trade) and hang it off the spine.

| Layer | What it is | Why it exists |
| ---| ---| --- |
| Tenant (account) | The RLS wall | Isolates the owner from any FUTURE-STATE commercial customer; hard security boundary |
| Profile (person) | The owner and each child | Per-person data, per-person views, per-person storage scoping |
| Entity (business) | Empire, UJG, JMR, Personal | Separates business books and business work from personal life |

### 5\. The 9 Spine Tables

Every row on every spine table carries `tenant_id`, plus `profile_id` and/or `entity_id` where relevant, plus the audit stripe in §9.

**5.1 —** **`actions`** **· THE UNIVERSAL UNIT**

Absorbs Tasks, the actionable half of Projects and Goals, `Clients.Next Action`, the SOP Library, all checklist prose, and all ~70 Daily Tracker habit columns.

| Column | Notes |
| ---| --- |
| `id`, `tenant_id`, `profile_id` | Identity and tenancy |
| `title`, `notes` | The thing itself |
| `kind` | task, project, goal, habit, routine\_step, sop, opportunity |
| `status`, `priority` | Single status field — see the collapse below |
| `area_id`, `hub_id` | FK to the taxonomy in 5.8 |
| `due_at`, `scheduled_for` | One date field each, not two |
| `parent_id` | Self-referencing hierarchy |
| `source_kind`, `source_id` | WHAT SPAWNED IT — a bill, a routine, a goal |
| `deep_link` | THE DO-NOW TARGET — jumps to where the Action gets completed |
| `completed_at` | The only input to goal progress |

Child tables:

| Child table | Purpose | Replaces |
| ---| ---| --- |
| `action_dependencies` | blocks / blocked\_by | FOUR separate self-relations in Notion |
| `action_templates` + `recurrence` | Cadence, next due, last done | SOP Library's Cadence / Next Due / Last Done, currently MAINTAINED BY HAND with no formula behind it |
| `action_logs` | `action_id`, `occurred_on`, `done` | THIS IS WHAT KILLS THE 70 CHECKBOX COLUMNS |

Collapses:

*   `Tasks.Status` + `Tasks.Assignment Status` → ONE field. Identical option sets, live data in both.
*   `Tasks.Date` + `Tasks.Dates` → ONE field.
*   Canonical Projects + Income Command Center Projects → ONE table.

Deletes:

*   `Tasks.Category` and `Missions."Associated with"` — rollups that copy the parent project's category down so a view can group on it. That is a JOIN in SQL.
*   `Projects.Total Tasks` — a count written as a formula only because Notion will not let a rollup feed arithmetic.
*   `Tasks.Schedule Day` and `Projects.Schedule Day` — the same expression maintained in two tables.

**5.2 —** **`events`** **· THE TIME LAYER**

Absorbs Timesheet (the only source table with a real start and end), Missions' Planned and Actual dates, Sprints.Dates, the day itself, and POMODORO SESSIONS, WHICH ARE RECORDED NOWHERE TODAY.

| Column | Notes |
| ---| --- |
| `id`, `tenant_id`, `profile_id`, `entity_id` | Identity and tenancy |
| `title` | — |
| `kind` | work\_session, focus\_block, routine\_run, appointment, trip, meal\_slot, bill\_due, day |
| `scheduled_start`, `scheduled_end` | Plan |
| `actual_start`, `actual_end` | Actual |
| `duration_min` | GENERATED |
| `action_id`, `template_id`, `area_id` | Links |

Child: `event_templates` — from the ⏱️ Blocks table (about 30 archetypes: ARCH, BUILD, DEBUG, SCHOLAR, TRADE, CEO, CLOSE, OPS, NIGHT-BUILD) plus its break pairing (Momentum 5min / Refuel 10min / Restore 15min), plus the 20 Day Schedules day-shapes.

CRITICAL GAP THIS CLOSES: ⏱️ Blocks has NO timestamp at all. It is a catalogue of archetypes, not a log. Nothing in the source system records "I ran The Builder from 8:30 to 9:00 today." The Pomodoro Framework page says so outright — when the app is built, every Pomodoro round will be logged.

PLANNED-VS-ACTUAL: Missions is the only source table that does this properly (Planned Dates / Actual Date, Planned Budget / Actual Budget). Generalizing that pattern to `events` lets Missions' two date columns collapse into one.

**5.3 —** **`days`** **· ONE ROW PER CALENDAR DAY**

MERGES Journal and Daily Tracker, killing two rollups outright (failure #1).

| Column | Notes |
| ---| --- |
| `date` | UNIQUE per profile |
| `day_type_id` | FK → `day_types` |
| `mood[]`, `energy`, `motivation`, `day_rating` | Daily scalars |
| `notes` | Short-form; long-form goes to `notes` |
| `cycle_phase` | — |

Hours, earnings and delivery totals become a VIEW over `events` and `transactions` — NOT stored rollups. Journal's Hours Today / Earned Today / Deliveries Today are rollups-over-formulas, the most fragile construct in the entire source model.

`day_types` becomes ONE table. It is currently defined in FOUR incompatible places: the Day Schedules page (20 types), `Journal.Type Of Day` (21 options), the Cycle-Synced page (7), and the Apple Shortcuts Day Launcher menu (12).

**5.4 —** **`notes`** **· THE NOTES STREAM**

Absorbs journal bodies, brain dump, dream journal, reflections, and `Tasks.Notes` / `Summary`.

| Column | Notes |
| ---| --- |
| `date`, `body` | The entry |
| `kind` | journal, brain\_dump, dream, reflection, record\_note |
| `tags[]` | Free taxonomy |

Child: `note_links` (`note_id`, `entity_kind`, `entity_id`) — ONE polymorphic link table replaces Journal's TEN separate relation properties.

**5.5 — MONEY ·** **`accounts`****,** **`transactions`****,** **`recurring_rules`****,** **`budgets`****,** **`buckets`**

ALMOST NONE OF THIS EXISTS IN THE SOURCE SYSTEM TODAY. Net worth is a prose sentence with a hand-calculated month-over-month delta. 25+ accounts are a markdown table of last-4 digits. The 5-bucket split (25/30/15/20/10 base; 25/30/45/0/0 sprint) — the central mechanic of the entire Money Hub — is FOUR STATIC TABLES, including a hardcoded table showing what each of five sample amounts splits into. 14 fixed bills carry hand-typed totals. Five abandoned Transactions tables date from 2025, none wired to anything.

| Table | Columns | What it replaces |
| ---| ---| --- |
| `accounts` | name, type, institution, last4, is\_synced | A markdown table of last-4 digits |
| `transactions` | account\_id, entity\_id, type, amount, category, occurred\_on | Five abandoned 2025 tables, none wired to anything |
| `recurring_rules` | label, amount, cadence, next\_due | 14 hand-typed fixed bills. SPAWNS Actions and Events; replaces "The Floor" |
| `buckets` + `bucket_rules` | effective\_from, sprint\_id, pct | The 5-bucket split becomes DATA instead of four static prose tables |
| `budgets` | Period envelopes | Hand-maintained targets |
| work-session view over `events` | total\_pay, net\_cash, $/delivery, $/hr\_effective as GENERATED columns from base\_pay, tips, deliveries, miles, expenses | The Timesheet formula chain (failure #3) |
| `mileage_rates` | tax\_year, rate\_per\_mile | THE IRS RATE IS CURRENTLY HARDCODED INSIDE A NOTION FORMULA and already disagrees between two pages, stated as the same value for two different tax years. A statutory constant that changes every January cannot live in a formula body |

**5.6 —** **`people`** **· CONTACTS**

Collapses THREE client tables into one: Clients (Income Command Center), CRM (the one Tasks and Projects actually relate to), and the contact fields smuggled onto Missions rows — Location, URL, Phone, Contact Email sitting on an event record.

**5.7 —** **`goals`** **+** **`missions`** **· THE LADDER**

`goals` keeps `start_value`, `end_value`, `target_date`.

PROGRESS STOPS BEING A STORED NUMBER. Today `Goals.Progress` = start ÷ end, and the Sunday Money Ritual instructs overwriting `Start value` weekly with the current balance — so every goal DESTROYS ITS OWN HISTORY each week, and there is no transaction log behind it. Progress becomes a view over completed `actions` and `transactions`.

`Goals."Days until due"` is `now()`\-dependent → a VIEW, never a stored generated column. Same for Missions' Date Countdown and Days passed, which are the same signed integer split into two positive-only columns.

**5.8 —** **`areas`** **+** **`hubs`** **· THE TAXONOMY**

The 9-value `Hub` multi-select is duplicated verbatim on FIVE databases — Projects, Goals, Resources, Missions, Blocks — and HAS ALREADY DRIFTED: Resources carries a 10th option ("Academic") the others lack. One lookup table, one foreign key.

Areas, fixed set: Self · Home · Money · Business · Academic · Kids · Spirit.

**5.9 —** **`resources`** **· THE LIBRARY, AND THE BIGGEST FINDING IN THE CRAWL**

ACADEMIC HQ CONTAINS NO ACADEMIC DATABASES. Courses, Assignments, Deadlines, Challenges, Academic Projects, Programs, Encyclopedias — all ELEVEN are filtered views of ONE generic Resources table, separated only by a `Type` select and a relative-date filter. There is no Course entity, no Assignment entity, no grade field, no credit-hours field, no term field, and no course→assignment foreign key. A course and an assignment are the same row shape.

Consequence: assignment due dates STRUCTURALLY CANNOT reach the daily dashboard today. `Resources.Date` is the only due-date field, and nothing joins it into the Tasks view that drives Today. The Academic HQ page states outright that calendar write access is denied and every trigger lives in the Resources DB only.

Split into: `resources` (library items) + `courses` + `assignments`, the last with real due dates that reach the Today surface.

| Classification | Definition | Examples | Handling / controls required |

| Public | Nothing in this app is public | — | N/A — no public surface exists |

### 12\. Data Flow & Lineage

The app talks to Postgres through the **Supabase client governed by RLS. There is NO hand-rolled REST API.** Server-side and scheduled work runs as **Supabase Edge Functions**.

| Data element | Source | Transformation | Destination(s) | Sync/Async | Frequency |
| ---| ---| ---| ---| ---| --- |
| Manual capture | App UI via Supabase client | Validation + tenancy stamp | `actions`, `notes`, `capture_inbox` | Sync | On demand |
| Habit tick | App UI | Insert, not column update | `action_logs` | Sync | On demand |
| Template / routine spawn | `action_templates`, `event_templates` | Bundle expansion | `actions` + `events` | Async — Edge Function | Scheduled |
| Pomodoro / block run | Timer UI | Start and stop stamps | `events` with actual\_start, actual\_end | Sync | On demand |
| Streak and consistency | `action_logs` | Aggregate | `v_habit_completion` | View | On read |
| Bill and recurring prompts | `recurring_rules` | Rule evaluation | `actions`, `events`, `notifications` | Async — Edge Function | Daily |
| Assignment due dates | `assignments` | Spawn Action with due\_at | `actions` → Today surface | Async — Edge Function | Daily |
| Work-session pay math | `events` | GENERATED columns from base\_pay, tips, deliveries, miles, expenses | `v_finance_summary` | Generated + view | On write / on read |

### 14\. Data Quality & Integrity

**THE ANTI-NOTION RULE — no duplicated formulas.** Computed values are produced in exactly one place, in this order of preference:

1. **Generated columns** for row-local math — `duration_min`, `net_cash`, trade PnL.
2. **Views / materialized views** for cross-row aggregates — everything Reports reads.
3. **Client selectors** for view-only display math that never persists.

Anything `now()`\-dependent — days-until-due, countdowns, days-passed — is a VIEW, never a stored generated column.

| Rule | Applies to | Definition | Enforcement point |
| ---| ---| ---| --- |
| Tenant scoping | Every table | `tenant_id` NOT NULL and matched to the authenticated tenant | RLS POLICY — database |
| Goal progress | `goals`, `missions` | Derived ONLY from `actions.completed_at` and `transactions`; NO writable progress column exists | View |
| Habits are rows | `action_logs` | A new habit is an INSERT, never an ALTER TABLE | Schema review |
| No cross-hub joins | Hub-private tables | A hub query may touch its own tables plus the spine, never a sibling hub's | Shared data-access layer + code review |
| Restricted gating | Health, medication, symptom, spiritual, intimacy | RLS plus app-level biometric gate; excluded from snapshots | RLS + app layer |
| Single formula home | All computed values | Row-local → generated column; cross-row → view; display-only → selector | Migration review |
| Statutory constants are data | `mileage_rates` and similar | Never embedded in an expression body | Schema review |
| Ordinals are numbers | Ratings, severities, priorities | Stored as integers with check constraints, never as emoji strings or mixed scales | Constraint — database |
| Area required | All spine records | Every record classifies into a life area | Constraint + UI default |
