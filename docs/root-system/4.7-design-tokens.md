### 1\. Overview

Tokens are the machine-readable layer under the design system in 4.5 and the visual identity in 4.6. They exist so that a design decision is made once, named once, and referenced everywhere — instead of being retyped as a literal value in forty places.

*   **Source of truth: CODE.** A single token module in the app repo, consumed through the NativeWind theme. There is no Tokens Studio file, no Figma variable set, no design-tool export step.
*   **Naming convention:** `category-property-modifier`, all lowercase, hyphen-separated. Flat and hyphenated rather than dotted, so names survive being pasted into class strings, documents and search without being mangled.
*   **Tiers:** RAW palette → SEMANTIC role → component usage. Components touch the semantic tier only.
*   **Platform:** React Native / Expo / TypeScript / NativeWind. One platform, one output.

#### 1.1 Why the source of truth lives in code

This is a deliberate choice for a solo builder, and it is worth naming plainly.

A token file that lives in a design tool has to be exported, transformed and kept in step with the code. With a team and a pipeline, that round trip is worth it. With one person building and shipping, it is a second system to maintain that produces no new information — and the failure mode is silent: the design tool says one thing, the app renders another, and nobody catches it because nobody is comparing them.

**A token file that drifts from the code is worse than no token file**, because it is trusted and wrong. So the code is the record. This page is the specification and the rationale; when they disagree, the code wins and this page gets corrected.

#### 1.2 The v2 migration

**Every raw colour token changed on 2026-08-26.** The app was built against the v1 seven-colour palette; UJG Color System v2.0 replaced it. Because every component references the SEMANTIC tier, the migration is a rewrite of §2 and a repointing of §3 — and nothing in `/components` changes. That is precisely the payoff §3.1 promised, collected on its first real test.

#### 3.1 The rule that makes all of this worth doing

**Components reference SEMANTIC tokens only. Never raw palette values. Never literal hex.**

This single rule is what buys three things:

1. **A palette migration is a one-file change.** The v2 migration on 2026-08-26 replaced every raw colour in the app and touched zero component files. Without the semantic layer it would have been an audit of `/components`, by hand, with a near-certain miss.
2. **Colours stop being hardcoded.** A literal hex in a component is invisible until it is wrong. With semantic tokens, a hex anywhere in `/components` is a review failure with no argument attached — the check is mechanical, not a judgement call.
3. **A contrast fix is one edit.** When a value turns out to fail AA, it is fixed in one place instead of hunted.

The rule holds through Phase 4 polish. The Afro-Futurist pass repoints tokens; it does not sprinkle hex.

#### 3.2 The three-way separation that replaced one overloaded colour

At v1, `accent-secondary` and `state-error` both pointed at Spanish Orange. Urgency and failure wore the same colour, and 4.6 flagged it as a real collision.

**v2.0 removes** **`accent-secondary`** **entirely** and separates the jobs:

| What it means | Token | Colour |
| ---| ---| --- |
| Pull the eye forward — do this now | `accent-primary` | Luminous Gold |
| Something needs attention soon | `state-warning` | Marigold |
| Something went wrong | `state-error` | Sunset Ember |

**Ember now means exactly one thing.** If Ember appears and nothing failed, that is a bug in the design, not a style choice.

**Residual risk:** Gold at hue 41° and Marigold at hue 34° are close. A warning must always carry an icon and a word; the two must never be adjacent as the only distinction between states. Tracked in 4.6 §10 item 8.

#### 3.3 Where the semantic names came from

The Root System's Book accents assign meaning to these colours — Platinum for meta and quality, Luminous Gold for explore and growth, Terracotta for commit and improve, Deep Amethyst for define, Sunset Ember for design, ship and close, Rich Forest for architect and run. The semantic assignments above follow that grain rather than cutting across it: gold pulls forward, forest runs underneath, platinum carries the information.

The one deliberate departure: **Ember's Book meaning includes "ship and close", which is good news.** In the app it means only failure. A Book accent is a label on a chapter; a state colour is a signal a tired person reads in half a second. The app's need wins, and the two meanings stay in their own documents.

### 4\. Spacing Tokens

**Base unit: 4.** Every spacing value is a multiple of it. The working step is 8 — the odd multiples exist for tight cases, not as a default.

| Token | Value | Typical use |
| ---| ---| --- |
| `space-0` | 0 | Reset |
| `space-1` | 4 | Icon-to-label gap, hairline separation |
| `space-2` | 8 | MINIMUM GAP BETWEEN TAP TARGETS · inline element spacing |
| `space-3` | 12 | Inner padding on compact rows |
| `space-4` | 16 | DEFAULT. Page gutter, card padding, standard vertical gap |
| `space-5` | 20 | Rare intermediate |
| `space-6` | 24 | Gap between grouped blocks |
| `space-8` | 32 | Gap between sections |
| `space-10` | 40 | Section break |
| `space-12` | 48 | Screen-level top and bottom breathing room |
| `space-16` | 64 | Empty-state vertical centring, generous spacing |

**Rule:** a spacing value that is not on this scale is not allowed. If a layout needs 14, either the scale is wrong or the layout is.

**Raised importance at v2.0:** 4.6 §3.5 establishes that this palette cannot produce a surface luminance step that separates a card from its ground. **Spacing and borders now carry the grouping work that fill luminance cannot.** The scale above is load-bearing, not cosmetic.

#### 5.5 The scaling requirement

**Every size in §5.2 must survive OS accessibility text scaling.** The device can scale type well beyond these values, and when it does:

*   No text may clip, truncate silently, or disappear behind another element.
*   No control may become unreachable because the layout grew.
*   Fixed-height containers wrapped around scalable text are a defect — heights grow with content.
*   Line-height tokens are multipliers, not fixed values, precisely so they scale with the text.

A size token is a base value, not a rendered promise. Anything that treats it as a fixed pixel truth breaks at the largest accessibility setting.

### 7\. Elevation Tokens

**Revised at v2.0.** The v1 model said elevation is carried by a step in surface luminance. Measurement says the palette cannot produce that step — see 4.6 §3.5. **Elevation is carried by border and spacing, with a small tint and a shadow as support.**

| Token | Surface | Boundary | Shadow | Use |
| ---| ---| ---| ---| --- |
| `elevation-0` | `bg-base` | none | none | The screen ground |
| `elevation-1` | `bg-surface` | `border-decorative` | very soft | Cards, list containers |
| `elevation-2` | `bg-elevated` | `border-decorative` | soft | Tab bar, sticky headers |
| `elevation-3` | `bg-elevated` | `border-meaningful` | pronounced | Sheets, modals, quick-add |

**Platform note:** React Native expresses shadow differently on the two platforms — iOS takes shadow properties, Android takes an elevation value. The token carries both, so a component asks for `elevation-2` and never for a platform-specific shadow object.

**On dark, a shadow on near-black does very little work.** Do not budget for it to. The boundary is what the eye reads.

### 9\. Opacity Tokens

**Reduced in scope at v2.0.** The v1 set used opacity to manufacture muted text, and that was the app's single biggest accessibility risk — an unverifiable value tuned by eye. v2 ships Muted Platinum as a real colour, so **opacity no longer produces any text value in this system.**

| Token | Value | Use | Risk |
| ---| ---| ---| --- |
| `opacity-full` | 1 | Default | — |
| `opacity-disabled` | 0.38 | Disabled controls | Disabled state is not required to meet text contrast, but it must not be invisible. Verify on device. |
| `opacity-pressed` | 0.80 | Press feedback overlay | Low |
| `opacity-scrim` | 0.60 | Behind sheets and modals | Must actually obscure — a weak scrim reads as a rendering bug |
| `opacity-surface-tint` | 0.30 to 0.60 | `color-forest-midnight` over Night for surfaces | PURELY AESTHETIC now. Card fill carries no AA obligation (4.6 §3.5), so this is tuned for warmth, not for separation. |
| `opacity-border-decorative` | 0.25 to 0.35 | `color-platinum-muted` for dividers and card edges | Tuned by eye is acceptable here — decorative boundaries carry no obligation |

**RETIRED:** `opacity-muted`. Replaced by `color-platinum-muted` at full opacity. Any code or design still computing muted text from an opacity is stale.

### 11\. Consumption in This Stack

| Layer | Where it lives | What it does |
| ---| ---| --- |
| Token module | A single TypeScript module in the app repo | The values. One file, exported as typed constants. THE SOURCE OF TRUTH. |
| NativeWind theme | `tailwind.config.js` | Maps the token module into theme keys so tokens are available as utility classes |
| Components | `/components` | Reference semantic token names through NativeWind classes, or the typed constants where a class will not do |
| Screens | The Expo Router tree | Compose components. Screens define no design values of their own. |

**How a value travels:** `color-gold` is defined once in the token module → `accent-primary` points at it → the NativeWind theme exposes `accent-primary` → the action row uses it. Changing the accent means editing one line, and nothing in `/components` is touched.

**What is forbidden:**

*   A literal hex value anywhere in `/components`.
*   A magic-number margin, padding, radius or duration.
*   An inline style object carrying a design value.
*   A component referencing a raw palette token instead of a semantic one.
*   A second token definition anywhere — including a design tool, a spreadsheet, or a copy of this page treated as authoritative.
*   **A retired v1 hex anywhere in the repo.** `#DCA424` `#E86100` `#5F2C82` `#7E3209` `#042D1D` are a grep-able build failure once the token module lands.

`FUTURE-STATE` — if the Command Core web app ever needs the same tokens, the token module gets extracted into a shared package. Not before there is a second consumer.

### 12\. What Is NOT Tokenized, And Why

Tokenizing everything is its own failure. A token set with three hundred entries is a lookup table nobody can hold in their head, and it produces the same drift it was meant to prevent.

| Not tokenized | Why not |
| ---| --- |
| SCREEN COMPOSITION AND RANKING ORDER | The cockpit's vertical priority order is a product decision that changes with what matters, not a design value. It lives in 4.1 §10 and 4.2. |
| COPY AND MICROCOPY | Words are content. They belong to 4.9. |
| ONE-OFF COMPONENT VALUES | A value used in exactly one place is not shared, so a token adds indirection with no payoff. If it gets a second use, it earns a token then. |
| ILLUSTRATION AND ICON ARTWORK | Assets, not values. They reference colour tokens; they are not tokens. |
| USER-SUPPLIED CONTENT COLOUR | Photos and user images are content. The system contains them; it does not restyle them. |
| ANIMATION CHOREOGRAPHY | Durations and easings are tokens. The sequence and staging of a transition is a component decision. |
| BREAKPOINTS | One column, one form factor at v2.0. Adding breakpoint tokens now would encode a layout system that does not exist. `FUTURE-STATE` with tablet. |
| SEMANTIC MEANING OF AREAS | Self · Home · Money · Business · Academic · Kids · Spirit are data, not design. They may map to a colour, but the mapping lives with the data model, not in the token set. |
| THE v2 TRIOS, GRADIENTS AND MOOD PALETTES | Color System v2.0 ships 20 trios, 40 gradients and 20 mood palettes. Those are COLLATERAL tools for decks, print and social. An app UI that reaches for a mood palette has stopped being a tool. |

### 13\. Governance

*   **Adding a token requires a reason.** One line in the change log: what it is, what could not be expressed with the existing set, and where it is used. No reason, no token. A token added because a value looked slightly off is how a scale rots.
*   **Adding a raw colour that is not in UJG Color System v2.0 requires a BRAND DECISION, not a code change.** A new hue is a conversation with 4.6 and the parent brand system, and it gets recorded there before a single line of code references it. **Deriving a tint or shade of a v2 colour is a code change** — `color-jungle-green-text` in §2 is the one existing example, and it is documented with its derivation and its measured ratio.
*   **Adopting an unused v2 colour into the app is a design decision, not a brand one.** Terracotta, Sage, Warm Sand, Clay Ember and Harvest Gold are already locked brand-wide; bringing one into the app UI needs a role and a contrast measurement, recorded here.
*   **Changing a semantic pointer is cheap and expected.** Repointing `state-warning` is a normal design decision. Changing a raw palette value is not.
*   **Renaming a token means updating every usage in the same change.** No aliases-for-a-release-cycle — with one consumer, that ceremony buys nothing and leaves dead names behind.
*   **Any colour change re-triggers contrast verification** for every pairing that colour participates in. See 4.6 §3.4.

| Change type | Requires | Impact |
| ---| ---| --- |
| New semantic token | Recorded reason · a named use case | Low |
| Repointing a semantic token | Contrast re-verification | Medium |
| Deriving a tint of a v2 colour | Derivation and measured ratio recorded in §2 | Low |
| Adopting an unused v2 colour | A role and a measured ratio recorded here | Medium |
| Introducing a hue outside v2 | A BRAND DECISION recorded in 4.6 first | Blocked by default |
| New spacing or size step | Proof the existing scale genuinely cannot express it | High bar — usually the answer is no |
| Renaming a token | Every usage updated in the same change | Medium |
| New theme | The full semantic set repointed and contrast-verified | `FUTURE-STATE` |
