### 1\. Executive Summary

The Life OS App is a **multi-tenant personal and freelance life operating system** — a cockpit that shows the control of someone's whole life and **drives daily action** instead of storing plans. It fuses Monarch (automated money and control), Notion (linked databases and knowledge), and Calendar (time as the axis) into one application.

The architecture is a **shared kernel, not distributed services**. One Postgres, one codebase. A **spine** of core entities — Actions, Events, Money, People, Goals, Notes, Areas, Automation, Templates — is an inherited platform layer that every hub uses through a shared data-access layer. Hubs are lenses over that spine, not silos. Each bounded-context hub owns its own private tables; **no hub reaches into a sibling's tables** — cross-hub needs go through the spine or an explicit interface. That is how "independent but connected" stays honest inside a single app instead of rotting into a distributed monolith.

**Actions are the universal unit.** Every plan, goal, bill, routine, and ritual decomposes into Actions, each carrying a do-now deep link to where it gets completed. Progress rolls up from completed Actions rather than being typed by hand. This is the difference between a thing that tells and a thing that does.

**Three-layer multi-tenancy is built from day one** — tenant (account) → profile (person) → entity (business). The RLS wall lives at the tenant layer. Retrofitting tenancy would be a rewrite; building it in makes the commercial Freelance Life OS release a config flag on the same codebase.

The app talks to Postgres through the Supabase client governed by RLS — there is no hand-rolled REST API. Anything server-side or scheduled runs as a Supabase Edge Function on `pg_cron`.

### 2\. Business & Solution Context

*   **Requirement (WHAT, not HOW):** a single owned application that runs a person's entire personal and freelance life — money, calendar, work, wellness, home, academics, family — as one connected system that drives action.
*   **Problem:** the Notion Command Center is the right system on the wrong engine. Formulas can't chain, automation isn't real, mobile capture is slow, there's no biometric privacy, recipes and measurements are weak, and it all rents on someone else's platform. The result **holds plans but makes nothing happen.**
*   **In scope:** the platform surface and four bounded contexts (see 4.1 Information Architecture), the shared spine, scheduled automation, Notion migration.
*   **Out of scope (v1):** web client · AI insights layer · public commercial multi-tenant launch (architecture ready, launch is Phase 7) · replacing ClickUp as UJG's freelance task/time source of truth · bank/Plaid auto-sync (manual entry + recurring rules first).
*   **Success criteria:** seven straight days run fully in-app, every in-scope record type spawning Actions, automation running unattended, on free-tier infrastructure.

### 3\. Architecture Drivers

#### 3.1 The deliberate trade-off

Fast / cheap / robust. **Chosen: ROBUST and CHEAP. Sacrificed: FAST.**

The app holds a whole life's data, must be owned and sovereign, and must be multi-tenant-ready to become a product — robust is non-negotiable. Solo and budget-bound means free tiers — cheap is forced and fine. Speed-to-ship is the deliberate sacrifice: a native build pipeline and a real data layer are slower than a throwaway PWA, but this is durable infrastructure, not a spike. **We buy correctness and ownership with time.**

### 4\. Architecture Overview

*   **Architectural style:** **shared-kernel modular application.** One Postgres, one codebase, an inherited spine, hubs as bounded contexts over it. Explicitly _not_ distributed services.
*   **Key patterns:** action-spine decomposition · one record, many views · RLS-as-authorization · scheduled idempotent jobs · optimistic offline writes with queued reconciliation · event rules (when X, create Action / send nudge) · templates that auto-spawn Actions and Events.
*   **The seam:** the shared spine is the stable boundary; hubs are swappable lenses over it. A hub can be added, reshaped, or dropped without touching the core. Deeper abstraction is deliberately deferred until a second tenant actually exercises it.
*   **Guiding principles:**
    *   **Actions or it didn't happen.** Anything that should be done becomes an Action.
    *   **No hub reaches into a sibling's tables.** Go through the spine or an explicit interface.
    *   **`tenant_id`** **on every row. RLS on every table. From day one.**
    *   **Computation in the database,** never duplicated formulas — the anti-Notion rule.
    *   **Migration before screen.**
    *   **Idempotent automation.**

### 7\. Integration & Interface View

**There is no hand-rolled REST API.** The app talks to Postgres through the Supabase client, every call constrained by `tenant_id` = the authenticated tenant, governed by RLS. Server-side and scheduled work runs as Edge Functions.

| Interface | Direction | Protocol | Auth |
| ---| ---| ---| --- |
| App ↔ Supabase | Bi | PostgREST / Realtime | Supabase JWT, RLS enforced |
| Edge Functions → Expo Push | Out | HTTPS | Expo push token |
| pg\_cron → Edge Functions | Out | HTTP invoke | Service role |
| Notion → Postgres (migration) | In, one-time | Idempotent scripts | Local run |
| Stripe or RevenueCat `FUTURE-STATE` | Bi | HTTPS | Phase 7 commercial only |
| ClickUp → Control Room `FUTURE-STATE` | In (read-only) | REST | Phase 7 |

Each third-party service: documented auth, watched rate limits, graceful offline fallback.

### 9\. Cross-Cutting Concerns

| Concern | Approach |
| ---| --- |
| Identity & tenancy | Supabase Auth, email OTP for v1. Session persisted in `expo-secure-store`. Recovery via email OTP. Three nested layers: tenant (the RLS wall, isolates Omegea from any future Freelance Life OS customer), profile (Omegea and each child), entity (Empire, UJG, JMR). |
| Roles | Owner — full CRUD on own tenant; manages profiles and entities; cannot see other tenants. Child profile — scoped read/write to own Kids records and assigned items only; cannot touch finances, business, or sensitive modules. Locked/sensitive — even the owner passes a fresh biometric check for Spiritual Practice and Intimacy. Customer `FUTURE-STATE` — owner-equivalent inside their own tenant only. |
| Security | PII is the owner's own life data in the owner's Supabase. TLS in transit, Supabase encryption at rest. Keys in `expo-secure-store`. No third-party data sale; export on demand. |
| Computation | The anti-Notion rule — generated columns → views → client selectors, in that order. Document any non-trivial calculation when added. |
| Automation | Edge Functions on pg\_cron: habit reset + streak recompute; daily cache and snapshot; hourly restock check; bill and routine prompts; weekly/monthly snapshots and milestone push. All idempotent — a double-run must not create duplicate Actions or charges. |
| Offline & sync | TanStack Query persistence + expo-sqlite cache; optimistic writes queued and reconciled on reconnect, last-write-wins for a single user. Local-first across all modules is `FUTURE-STATE` Phase 7. |
| Observability | Supabase logs + Sentry for client and function errors with alert thresholds; uptime watch on Edge Functions. Reviewed weekly alongside the §2 metric events. |
| Feature flags | A simple flag table the owner flips. |
| Design | Responsive; every state (loading / empty / error); WCAG 2.1 AA; Afro-Futurist palette — Night, Dark Green, Eminence, Spanish Orange, Goldenrod, Platinum, Sienna. |
| Analytics | `action_completed`, `money_logged`, `habit_checked`, `routine_run`, `focus_session`, `onboarding_completed` — each with properties. See 10.3. |

### 10\. Failure → Acceptance → Test (the wired spine)

This chain is the regression core. Full strategy in 7.1.

| # | Failure | Acceptance | Level |
| ---| ---| ---| --- |
| 1 | Tenant isolation breach | Given a user, when querying another tenant's row, then RLS blocks it, no leak | Integration |
| 2 | Auth expires mid-action | Given an expired session, when acting, then re-auth and state preserved | Integration |
| 3 | Sensitive module bypass | Given the lock, when opening Intimacy/Spiritual without biometric, then blocked — nothing rendered or cached | Integration |
| 4 | Offline write conflict | Given two offline edits, when reconnecting, then resolved per last-write-wins | Integration |
| 5 | Bad input | Given invalid data, when submitting, then validation rejects, no write | Unit |
| 6 | Automation double-run | Given a scheduled job re-fires, then idempotent — no duplicate Actions or charges | Integration |

### 12\. Alternatives Considered

| Option | Why not chosen |
| ---| --- |
| Next.js PWA (simpler, skill-aligned) | iOS reliability for push, real biometrics, and offline are must-haves a PWA can't deliver |

### 14\. Roadmap & Evolution

*   **Most likely to change in ~3 months:** the hub feature set — which modules exist, what each tracks, and final tech choices that solidify later. The spine absorbs that change; the hubs are the swappable part.
*   **`FUTURE-STATE`** **Phase 7:** web companion (React Native Web on the same code) · AI insights layer · commercial Freelance Life OS tenant · local-first offline · read-only ClickUp sync.
*   **Kill criteria:** if after the one-week beta daily friction is higher than Notion's, **stop and re-scope before adding modules.**
