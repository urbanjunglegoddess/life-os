### 1\. Purpose & Scope

These are the writing and formatting rules for every page in the Application Root System — all 183, in ClickUp doc `838qa-88931`. They apply to filled pages and to ⚪ Template skeletons alike. Two readers are being served at once: Omegea in a build session, and Claude Code loading a page as context at the start of a slice. A page is good when both can act on it without asking a question. Out of scope: the app's own in-product copy, `README.md` files in the repo, and UJG client-facing writing, which follows the UJG brand voice instead.

### 2a. The Scaffolding Rule

Elements 1 through 10 — the metaphor line, the description, the guiding questions, the activities, the outline, the links, and the Done When checklist — are KEPT VERBATIM when a page is filled. They are not scratch to delete once the answer exists. They are the reasoning that produced the answer: what question was being asked, what work was done to answer it, and what standard the answer had to meet. Deleting them leaves a conclusion with no visible argument, and six months later nobody can tell whether the conclusion was reasoned or guessed. The only line that changes above the divider is the status line, and the only line that changes on the divider is the italic sentence after the CAPS verb.

### 3\. Voice & Tone

*   **Voice:** Direct and concrete. Present tense, active voice. Short sentences carrying real information.
*   **No padding:** No "great question," no "it is important to note that," no restating the section heading as its first sentence, no closing summary of what was just said.
*   **No hedging:** "Maybe consider thinking about" is dead language. If a thing is decided, say it is decided. If it is not, say it is not.
*   **Say what is unknown:** An unknown written as "UNKNOWN — decided when the schema for X lands" is useful. An unknown papered over with plausible-sounding content is a defect that will be believed and built on. Never invent content to make a page look finished.
*   **Reasons, not just rules:** Where a rule is non-obvious or was learned by getting burned, write the burn. Section 7 exists entirely for this reason.
*   **Not the UJG brand voice:** This system is internal build documentation. The warm, conversational UJG voice belongs on the website and client-facing work. Here, terseness is the courtesy.

| Do | Don't |
| ---| --- |
| Supabase RLS enforces tenant isolation at the row level. | It should be noted that RLS is generally considered a best practice for handling multi-tenancy concerns. |
| UNKNOWN — the offline sync strategy is not decided. Blocked on the mobile storage spike. | The offline sync strategy will likely involve some form of local caching. |
| Marked `FUTURE-STATE`: push notifications. Trigger — the first non-Omegea tenant. | Push notifications are part of the platform surface. |
| Delete the row. | This row is not applicable at this time and has been retained for completeness. |

### 5\. Document Structure Rules

*   **Headings:** Exactly one H1 per page, the page title. Workbook sections are H2. Filled-document sections are H3, numbered from 0 (Document Control). Never skip a level.
*   **Section order:** Fixed by section 2. Document Control is always section 0. The Change Log is always last.
*   **Numbering:** Filled-document sections carry numbers so a page can be cited precisely — "0.3 section 7" beats "the ClickUp part of the style guide."
*   **Length:** No target length. A page is as long as its content and not one line longer. A three-row table beats three paragraphs describing the same three things.
*   **Placeholders:** ZERO bracketed placeholders may survive in a filled page. Every prompt is either replaced with real content or the row is deleted. A leftover bracket is the single clearest sign a page was abandoned mid-fill.
*   **Deleting rows:** Delete template rows that genuinely do not apply. When the deletion is meaningful — a whole governance role that does not exist, a review cadence that was rejected — say in italics why it was cut rather than leaving the reader to wonder if it was an oversight.

| Use… | When |
| ---| --- |
| Prose | Rationale, history, a decision that needs its reasoning carried with it. |
| Bulleted list | Rules, constraints, unordered options. |
| Numbered list | Sequential procedures only. |
| Table | Comparisons, registers, matrices, enums, anything with more than two parallel attributes. THE DEFAULT for structured content in this system. |
| Fenced code block | Schema, commands, file paths in quantity, state diagrams. |

### 6\. Formatting Conventions

| Element | Convention | Example |
| ---| ---| --- |
| Dates | ISO 8601 in front-matter and Change Logs. NO calendar dates in body content — the build runs on effort-based phase gates, and every future-state item names a TRIGGER, not a date. | 2026-08-23 |
| Filenames | ALWAYS in backticks. Never bare. See section 7 hazard 1. | `CLAUDE.md` · `README.md` · `package.json` |
| Database references | Backtick the table-dot-column form, and write it lowercase — capitalized dotted words get linkified even inside backticks. | `tenants.id` · `actions.tenant_id` |
| ClickUp and repo IDs | Backticked. List `901110966415` · space `90113838314` · doc `838qa-88931`. | `UJGFREE-0142` |
| Emphasis in body text | Bold for a defined term on first use. Italic for an aside or a caveat on a checklist line. | — |
| Emphasis inside table cells | ALL-CAPS. Inline bold does not survive. See section 7 hazard 2. | NEVER · OMEGEA ONLY · CURRENT STATE |
| Enum lists | Separate with a middle dot. Do not use escaped pipes inside table cells. See section 7 hazard 3. | Full · Partial · Skip · Future-state · Paused |
| Status markers | The literal strings, backticked, inline where they apply. | `FUTURE-STATE` · `PAUSED` |
| Callouts | Blockquote for a rule that must not be missed. Used sparingly — everything on the page matters, so a callout on every third line means nothing. | — |
| Long entries in a table | A cell is for a short entry. Anything approaching a paragraph goes in prose under the table. See section 7 hazard 7. | — |

### 6a. Checkbox Honesty

The Done When checklist is a claim about reality, not a progress bar. Tick a box only when it GENUINELY passes. When a box does not pass, leave it unticked and write the reason in italics on the same line — what is missing and what unblocks it. An unticked box with a stated reason is a finished thought; an unticked box with no reason is an open question nobody is holding. Never tick a box to make a page look complete: the cost of a false tick is that the next reader stops checking, and this system has exactly one reader who could catch it.

The most common honest miss in this system: the register box. A page can be fully written, approved, and 🟢 Active while its row in 0.6 does not exist yet. That box stays unticked and says so, because a filled page without a register row is an unfinished slice.

### 7\. CLICKUP RENDERING HAZARDS

_Learned the hard way during the port from the source documentation set. Every one of these has actually bitten — hazards 1 and 4 bit this very page on its first save. Read this section before writing or updating any page._

| # | Hazard | What happens | The rule |
| ---| ---| ---| --- |
| 1 | Bare filenames and dotted identifiers | ClickUp auto-linkifies anything shaped like a domain. A bare mention of CLAUDE dot md becomes a broken link to an http address, and the reader clicks it. Backticks help but do NOT always save you — a capitalized dotted pair like Table dot Property gets linkified inside backticks too. | BACKTICK every filename and dotted identifier, keep them lowercase, and re-read after saving. If it still linkifies, spell the dot out in words. |
| 2 | Bold inside table cells | Inline bold delimiters are STRIPPED on save inside a table cell. The emphasis silently vanishes and the sentence loses its stress. | Use ALL-CAPS for emphasis inside tables. Never rely on bold there. |
| 3 | Escaped pipes in table cells | An escaped pipe gets UNESCAPED on round-trip and is then read as a column separator, splitting the row into extra columns and wrecking the table. | Never put a pipe inside a table cell, escaped or not. Separate enum values with a middle dot. |
| 4 | Bold or italic next to a code span | A bold or italic delimiter sitting between a code span and punctuation gets re-escaped into literal asterisks on save, and the reader sees stray asterisk characters in the text. | Do not put emphasis delimiters immediately adjacent to a code span. Restructure the line — move the code span mid-sentence, or use an em dash instead of an emphasized label ending in a colon. |
| 5 | No incremental patch | There is NO partial update on doc pages. Every update reconstructs and resends the ENTIRE page. A partial send silently replaces the whole page with only what was sent. | Read the page, modify the full content, resend the whole thing. Then RE-READ to verify nothing was lost. The re-read is mandatory, not optional. |
| 6 | Docs API throttling | The docs API throttles harder than the tasks API. Rapid successive page writes fail or land partially. | Work one page at a time, verify each before starting the next. Do not batch page writes. |
| 7 | Oversized single table cell | A cell carrying roughly 1,500 characters or more gets the WHOLE page write rejected — with the same bare Bad Request a malformed row produces. The symptom is indistinguishable from a cell-count error, so it sends you recounting pipes that were never wrong. | Keep rows SHORT. When an entry needs a paragraph, leave a one-line summary in the cell and move the long text to a prose block directly under the table. A dense numbered first column can be dropped as a precaution. |

**On hazard 7, because the failure lies to you.** It was found on 2026-08-26 writing a long change-log entry into a single cell on 4.8. Nothing in the response distinguishes an oversized cell from a broken row, so the obvious move — recounting the pipes on every row — burns the time and finds nothing. When a write fails and the row counts are provably right, look at the LONGEST cell on the page before looking anywhere else. The fix is never to shorten the writing; it is to move the writing out of the table, where it reads better anyway.

### 8\. Diagram Conventions

*   **Tool of record:** Fenced code blocks inside the page itself. A diagram that lives in an image file goes stale the day the architecture changes, because nobody opens the source. Text diagrams get edited because they are already open.
*   **Notation:** Plain ASCII arrows for state and flow. Crow's-foot notation described in text for entity relationships; the authoritative schema is the Supabase migration, and Book 5 pages link to it rather than redrawing it.
*   **Where sources live:** In the page. There is no separate diagram repository — that is `FUTURE-STATE`, triggered by the first diagram too complex to render as text.
*   **Styling:** Book accent colors are referenced by name and hex in the metaphor line only. Diagrams stay monochrome — color carries no meaning in this system.
*   **Accessibility:** Never encode meaning in color alone. Every status badge carries its label in text next to it, which is why the convention is "🟢 Active" and never a bare 🟢.

### 9\. Accessibility & Inclusive Language

Meaningful link text — never "click here" and never a raw URL as the visible text. Heading structure must be real hierarchy, not visual sizing. Status is always badge plus word. Plain language over jargon; where a term of art is unavoidable, define it on first use and add it to 0.9 Glossary. Write about the reader as "you" and about the builder by name.

### 10\. Templates & Where They Live

Every new page in this system STARTS FROM A TEMPLATE — the 183 skeletons ship with the Root System and are adopted as the build reaches them. There is no blank-page start. A page is filled by writing below the ALL-CAPS action divider and leaving everything above it intact. The Templates Index at 0.8 will list every template and its intended Book; it is still ⚪ Template, so that index is `FUTURE-STATE` and today the templates are discovered by browsing the Book structure directly. Trigger — the first time a template is needed that does not already exist in the 183.

### 11\. Governance & How to Use

This guide is enforced by reading it, by one person. There is no linter and no review board — ONE PERSON holds every role. Omegea Hunter is owner, author, reviewer, and approver of every page; Claude Code drafts and updates pages as part of the slice it is working and has NO approval authority. Compliance is checked during the phase-gate sweep, when every filled page is walked. Exceptions are not requested from anyone — Omegea either changes the rule here or the page follows it. Changes to this guide bump the version in BOTH the blockquote and section 0 Document Control, add a Change Log row, and update the matching row in 0.6 in the same slice. When this guide and a page disagree, the guide wins and the page is corrected.
