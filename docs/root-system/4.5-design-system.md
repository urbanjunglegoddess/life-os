### 1\. Overview

This is the component system for the **Life OS App** — a mobile-first React Native app on Expo, TypeScript, Expo Router and NativeWind, replacing the Notion Omegea Command Center documented in 4.1.

**Source of truth is code.** There is no Figma library and no published package. Components live in `/components` in the app repo, styling comes from the NativeWind theme built on the tokens in 4.7, and this page is the register that says what exists and what it owes. This is a deliberate choice for a solo builder: a second source of truth in a design tool would drift from the code within a week, and a drifted library is worse than none.

**Phasing.** The system is built in **Phase 2** (UJGFREE-5894). **Phase 4** is the polish and Afro-Futurist pass — texture, motion character, and visual refinement land there, on top of components that already work. Nothing in Phase 4 is allowed to change a component's contract.

*   **Platform:** React Native / Expo · TypeScript · Expo Router · NativeWind
*   **Accessibility target:** WCAG 2.1 AA (see 4.8)
*   **Current version:** v1.0 specification · **Release cadence:** none — the library versions with the app

### 2\. Design Principles

These are enforcement rules, not aspirations. Each one can be used to reject a component in review.

| Principle | What it means | What it looks like in practice |
| ---| ---| --- |
| MOBILE-FIRST, ONE COLUMN | A phone is one column. The source system tiled eleven cockpit surfaces across three desktop columns; the app cannot. | No side-by-side layouts. No horizontal scrolling for primary content. Tablet and wide layouts are `FUTURE-STATE`. |
| RANKED, NOT TILED | Order is the design decision. If everything is equally visible, nothing is prioritized. | Every screen has an explicit vertical priority order recorded in 4.2. A new panel has to displace something, not squeeze in. |
| EVERY SURFACE LEADS SOMEWHERE DOABLE | A component that only displays information has to justify itself. | Cards, rows and stat tiles carry a destination. Read-only surfaces are the exception and get named as such. |
| TAPS-TO-LOG IS THE PRIMARY METRIC | The number of taps required to capture or log is how this system is measured. Not beauty, not density. | Capture is one or two taps. Habit and routine logging is one tap. Any change that adds a tap to a logging path is a regression and gets rejected. |
| NOTHING DECORATIVE COMPETES WITH THE DO-NOW ACTION | Ornament that draws the eye away from the next doable thing is a defect. | The do-now affordance is the highest-contrast element in its row. Texture, gradient and flourish sit behind content, never beside the action. |
| EVERY COMPONENT SHIPS THREE STATES | Loading, empty and error are part of the definition of done — not polish, not Phase 4. | A component without all three does not merge. See §6. |
| NO HARDCODED VALUES | Colour, spacing, radius, type and duration come from tokens. | A literal hex, a magic number margin, or an inline duration fails review. See §9. |

### 3\. Foundations

*   **Layout:** single column. Page gutter 16. Vertical rhythm from the spacing scale in 4.7. Content runs full width minus gutters; there is no column grid on phone.
*   **Base unit:** 4, with 8 as the working step. All spacing references tokens (4.7 §4).
*   **Colour, type, radius, elevation, motion:** tokens only (4.7). Semantic tokens, never raw palette values.
*   **Safe areas:** every screen respects the device safe area at top and bottom. The tab bar sits inside the bottom inset; sheets account for the home indicator.
*   **Iconography:** one icon set, one weight, 24 nominal size, 20 for inline and 28 for tab bar. Icons are never the only carrier of meaning — every icon-only control has an accessible label. Set selection and stroke are specified in 4.6 §5.
*   **Theme:** dark base only at v1.0. A light theme is `FUTURE-STATE` and is the reason the semantic token layer in 4.7 exists.

The register. Every component the product actually needs, not only the nine named in the build plan. States listed are the states the component must implement before it can merge.

**Register rules.** Every component above must list all its states before it is built. States are not discovered during the build — a missing state in this table is a specification defect, not an implementation detail.

### 5\. Tap Target Sizing & One-Handed Reach

This is a functional requirement. The core interaction of this app is repeated tapping on a phone, often one-handed, often at 6am. A target that is a few points too small is not a visual flaw — it is a failed log.

**Minimums**

*   **48 x 48 minimum** for every interactive element. Stored as the `tap-target-min` token in 4.7 so it cannot drift.
*   **8 minimum spacing between adjacent targets.** Two logging controls close enough to mis-tap is a defect.
*   **Hit slop is allowed to exceed the visual size.** A 24 icon can carry a 48 target. Visual weight and touch size are separate decisions.
*   **The visible label is inside the target.** Text that describes a control but sits outside its touch area does not count.

**Reach**

| Zone | Where it is | What belongs there |
| ---| ---| --- |
| EASY | Bottom third of the screen, inside the thumb arc | Tab bar · quick capture · sheet primary actions · habit and routine logging · anything tapped repeatedly |
| STRETCH | Middle of the screen | Content, list rows, cards — read first, tapped deliberately |
| HARD | Top corners, especially the far corner from the thumb | Back · settings · secondary utility. Nothing repeated, nothing urgent. |

**Rules that follow from this**

*   Primary actions in sheets sit at the bottom, not the top.
*   Destructive actions are never adjacent to a high-frequency logging target.
*   The quick-add control is reachable one-handed from every screen. If it is not reachable, the one-or-two-tap capture promise is already broken.
*   Long-press is never the only way to do something. It is an accelerator, never the sole path.
*   `FUTURE-STATE` — a left-handed reach check once the cockpit ranking in 4.2 is locked.

### 6\. The States Rule

**Every component ships loading, empty and error. This is part of the definition of done, not polish, and not Phase 4 work.** A component that renders only its happy path does not merge.

The rule exists because the previous system had no way to express these states at all — twelve panels in the source were specified and abandoned because the tool could not compose them (4.1 §1.5). An app that owns its own rendering has no excuse.

#### 6.1 Worked example — the Today Actions list on the cockpit

**LOADING**

*   Three to five skeleton rows at the real row height, so the layout does not jump when data lands.
*   Skeletons carry no text and no placeholder numbers. A greyed-out fake value reads as real data for the half-second before it is replaced.
*   The screen shell, header and tab bar stay interactive. Loading a list does not lock the app.
*   Announced as busy once. Not on every frame.
*   A spinner appears only if the wait exceeds the threshold where a skeleton starts to look broken. Skeleton first, spinner as the exception.

**EMPTY** — three different empties, three different messages:

| Kind of empty | What it means | What the user sees | The one action offered |
| ---| ---| ---| --- |
| NOTHING-TODAY | Everything due today is done | A confirmation that the day is clear — this is a WIN state, not a failure state | Plan tomorrow, or capture something |
| NOTHING-YET | No Actions exist at all — new profile, new hub | An explanation of what an Action is and where it comes from | Add the first Action |
| FILTERED-TO-NOTHING | Data exists but the current Area or entity filter excludes it | A statement that the filter is hiding results, naming the active filter | Clear the filter |

Collapsing these three into one generic no items message is the failure mode. The first is a success, the third is a user mistake, and they must not look alike.

**ERROR**

*   Says what failed in plain language: could not load today's actions.
*   No error codes, stack traces or raw messages in the primary text. A code may sit in a secondary line for the builder's own debugging.
*   **Last-known cached data stays visible where it exists**, marked stale, above the error. Losing the screen's content because a refresh failed is worse than the failure.
*   Retry is a real labelled control that meets the tap-target minimum.
*   Offline is a distinct case: it says offline, not error, and it names the pending-write count so the offline queue is never invisible.
*   Announced politely. One announcement, not a loop.

### 7\. Patterns

| Pattern | Problem it solves | Components used | Rules |
| ---| ---| ---| --- |
| One-or-two-tap capture | Getting a thought out of the head before it is lost | Quick-add sheet · money entry field · chip | Reachable from every screen. Opens focused with the keyboard up. Submits with one control. Never blocks on a field the user does not have yet. |
| Do-now deep link | Turning a listed Action into a completed one without hunting | Action row · screen shell | Every Action carries a destination. The link goes to where the work actually happens, not to a detail page about the work. |
| One-tap logging | Habits and routines logged without a form | Habit tap target · routine checklist item · offline pending badge | One tap, optimistic, reversible. Undo is available for a short window. Pending writes are visible. |
| Ranked cockpit | Eleven proven surfaces, one phone column | Screen shell · stat strip · card · action row · section header | Priority order comes from 4.1 §10 and 4.2. Ranking is data-driven where possible — what is due beats what is merely present. |
| Offline write | Acting with no connection and not losing it | Offline pending badge · action row · error state | Optimistic UI plus a visible pending signal. Pending is never styled to look confirmed. Failures surface where the record lives, not only in a global toast. |
| Gated surface | Sensitive content that must not render before authentication | Biometric gate screen · screen shell | Nothing renders behind the gate. No cached preview, no app-switcher snapshot of content. Fresh check on entry, not a session flag. |
| Context switch | Knowing which profile and which books you are in | Entity switcher · profile switcher · section header | Active context is visible without opening the switcher. Changes are announced. Money and work surfaces always show the entity. |
| Three-state list | Any list, anywhere | List row · loading state · empty state · error state | §6 applies without exception. |

### 8\. Accessibility Standards (system-wide)

*   **Target:** WCAG 2.1 AA. Full criteria and the audit approach live in 4.8.
*   **Touch:** 48 minimum, from the `tap-target-min` token. See §5.
*   **Contrast:** this is a dark-base design. Every accent-on-dark pairing is contrast-checked, not assumed. See 4.6 §3 — goldenrod and orange on near-black are the pairings most likely to fail for small text.
*   **Text scaling:** every component must survive OS accessibility text scaling without clipping or losing a control. Fixed-height containers around scalable text are a defect.
*   **Colour is never the only signal.** State, status, trend and selection each carry text, shape or icon in addition to colour.
*   **Screen reader:** every interactive element has an accessible label describing the ACTION, not the icon. Headings are real headings. Live regions are used sparingly and politely.
*   **Motion:** reduced-motion preference is respected. No component depends on animation to convey meaning.
*   **Focus:** focus moves into modals and sheets on open and returns to the trigger on close.

### 9\. Tokens Reference

Design Tokens (4.7) is the single source of truth for every value. Components consume the **semantic** layer — `bg-surface`, `text-primary`, `accent-primary`, `border-subtle`, `state-error`, `focus-ring` — through the NativeWind theme.

**Nothing hardcodes a colour.** A literal hex value anywhere in `/components` is a review failure, with no exception for one-offs and no exception for Phase 4 polish. The same applies to magic-number spacing, ad-hoc radii and inline animation durations.

The reason is concrete: the semantic layer is what makes a light theme, a high-contrast theme, or a contrast fix possible as one edit instead of a repo-wide hunt.

### 10\. Governance & Contribution

Solo build, so this is a discipline, not a committee.

*   **Location:** components live in `/components`. Screens live under the Expo Router tree and compose components; screens do not define reusable UI inline.
*   **Styling:** driven by tokens from 4.7 via the NativeWind theme. No inline style objects carrying design values.
*   **A new component needs a reason recorded before it enters the library.** One line in §11 below: what it is, what existing component could not do the job, and where it is used. No reason recorded, no component. This is the whole defence against a library that grows to forty half-used pieces.
*   **Before merge, a component must have:** all variants, all states including loading, empty and error, an accessible label strategy, tap targets meeting the minimum, and zero hardcoded design values.
*   **Deprecation:** a component being retired keeps a migration note in §11 until every usage is gone.

| Change type | Requires | Impact |
| ---| ---| --- |
| New component | Recorded reason in §11 · states and variants defined first | Library grows — needs the register updated |
| New variant | A named use case | Low |
| New state | Update this register FIRST, then build | Low |
| Breaking change to a component contract | Every usage checked and updated in the same change | High |
| New token | Goes through 4.7 governance, not through a component | See 4.7 §12 |
| New raw colour outside the locked palette | A BRAND DECISION, not a code change. See 4.6. | Blocked by default |
