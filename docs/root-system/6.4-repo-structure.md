## ⚠️ READ THIS BEFORE CHANGING ANY FOLDER

This repository is a MONOREPO. It has `apps/` and `packages/` directories and they are correct.

Versions v1.0 and v1.1 of this page mandated a flat single-app layout (`/app`, `/lib`, `/db`) and explicitly forbade `apps/` and `packages/`. That guidance was SUPERSEDED on 2026-09-07 by ADR-0014. It is preserved below, labelled, for the record.

An agent or contributor reading this page MUST NOT "restore" the flat layout, MUST NOT delete `apps/` or `packages/`, and MUST NOT treat the presence of those folders as drift to be corrected. The monorepo is the intended, shipped state.

### 1\. Overview & Decision — CURRENT

The Life OS App is ONE repository holding TWO deployable applications and TWO shared packages, on a single Supabase Postgres. It is a MONOREPO.

WHY IT CHANGED. The product now needs a small Next.js web app alongside the Expo app. Google Play mandates a publicly accessible account-deletion URL that is reachable outside the app, separate from the in-app deletion path. Both stores additionally require privacy-policy and terms links in store metadata AND in-app. Those pages have to live on the public web, which means a second deployable target. A second deployable target is no longer optional, so a flat single-app repo can no longer express the project. ADR-0014, dated 2026-09-07, converted the repo.

WHAT DID NOT CHANGE. One database. One tenancy model. One design-token source. One owner. The monorepo buys a second deploy target and shared types — it does not buy team autonomy, independent release trains, or per-package versioning, none of which exist here.

`FUTURE-STATE` — A fuller web companion (React Native Web running the mobile code) remains Phase 7. `apps/web/` today is compliance pages ONLY. Expanding it into a product surface is a new ADR, not a quiet scope creep.

`PAUSED` — Payload CMS was evaluated and DROPPED in ADR-0003. It is NOT in the layout and must not be re-added. If content management resurfaces it re-enters through a new ADR, not by restoring a folder from an old diagram.

| Attribute | Value |
| ---| --- |
| Model | MONOREPO — two apps, two shared packages, one database |
| Deployable targets | `apps/mobile` Expo · `apps/web` Next.js compliance pages |
| Repo host | GitHub (CI on GitHub Actions) |
| Mobile build | Native Expo tooling — EAS Build / EAS Update |
| Web build | Next.js build and deploy |
| Orchestration | NONE yet — no Nx, no Turborepo, no Bazel. Add one only via ADR |
| Package manager | npm workspaces — root `package.json` declares `apps/*` and `packages/*` |

`SUPERSEDED` v1.0–v1.1 · superseded 2026-09-07 by ADR-0014 · The prior decision read: "ONE repo holding ONE codebase — a React Native (Expo, TypeScript) app on a single Supabase Postgres. Not a monorepo with packages. Not distributed services. A shared kernel: one app, one database, one deploy path." Its stated reason was that package boundaries buy team autonomy and independent deploys, neither of which existed for a solo build, while charging daily in build config and context-switching. That reasoning was sound for a single deployable target and is retained here because it still governs how MUCH structure to add: the repo splits only where a real second target forces it, and no further. It stopped holding the moment store compliance required a publicly reachable web page. The prior page also stated "There is no `/packages`, no `/apps`" and that "Shipping web does NOT convert this repo to a monorepo." Both statements are now FALSE and must not be acted on.

Notes on the tree, kept out of the table on purpose.

`apps/web/` is deliberately tiny. It exists because Google Play requires an account-deletion URL a user can reach without installing the app, and because both stores require privacy and terms links in metadata as well as in-app. Do not grow it beyond those three routes without an ADR.

`packages/types/` is GENERATED from the database schema. Do not hand-edit files in it. Regenerate after every migration; a drifted type is a silent bug that reaches both apps at once.

`packages/tokens/` is the single source of truth for design tokens. Both apps consume it. A colour or spacing value defined anywhere else is a defect.

`docs/root-system/` is a READ-ONLY MIRROR of the Root System pages that govern slice one. ClickUp is the source of truth. Edits belong in ClickUp and flow down to the mirror, never the other way.

`CLAUDE.md` is GENERATED FROM PAGE 6.2 and is read automatically by Claude Code at the start of every session. Editing it by hand puts the repo and the Root System out of sync. Change 6.2, then regenerate.

### 3\. Module / Package Boundaries — CURRENT

Boundaries are now a mix. `apps/*` and `packages/*` are real npm workspace boundaries. Everything inside an app is still a FOLDER boundary enforced by review, not tooling.

| Unit | Purpose | Public surface | May depend on | Must NOT depend on |
| ---| ---| ---| ---| --- |
| `apps/mobile` | Expo app — all product surfaces | Shipped app | `packages/types` · `packages/tokens` | `apps/web` |
| `apps/web` | Next.js compliance pages ONLY | `/delete-account` · `/privacy` · `/terms` | `packages/types` · `packages/tokens` | `apps/mobile` |
| `packages/types` | GENERATED DB types | Exported TypeScript types | Nothing — generated output | Both apps. Never imports app code |
| `packages/tokens` | Design tokens | Exported token values | Nothing | Both apps · both other packages |
| `supabase/` | Migrations and RLS tests | Applied schema + policies | — | Everything. It is data, not code |
| `scripts/` | CI and ops scripts | CLI invocation | — | App source |
| `docs/` | Spec + read-only Root System mirror | Reading | — | — |
| `apps/mobile/app/{hub}` | Screens for one hub | Routes | Own app `components` · `lib` | ANOTHER HUB'S FOLDER · direct table reads outside its own hub |
| `apps/mobile/components` | Shared UI + design system | Exported components | `lib` types and utils · `packages/tokens` | `app` — components never import screens |
| `apps/mobile/lib` | Supabase client · SHARED DATA-ACCESS LAYER · hooks · utils | Exported query and mutation functions · hooks · client | Supabase SDK · `packages/types` | `app` · `components` |

THE HARD RULE, UNCHANGED. NO HUB REACHES INTO A SIBLING HUB'S TABLES. Every hub reaches the spine through the shared data-access layer in `apps/mobile/lib`. Cross-hub needs go through the spine or through an explicit interface exported from that layer — never a direct query against another hub's tables, and never an import from a sibling hub folder.

THE NEW RULE. THE TWO APPS DO NOT IMPORT EACH OTHER. Anything both apps need is promoted into `packages/`. `apps/web` in particular must stay thin enough that it never needs mobile code.

_Dependency direction inside the mobile app is unchanged: app → components → lib. Enforced by CONVENTION AND REVIEW. The workspace boundary between apps and packages is the only part the tooling actually enforces, which is exactly why the rest is written down here._

### 4\. Shared Code

*   CROSS-APP shared code lives in `packages/`. There are exactly two packages and both are deliberate.
*   `packages/types` — TypeScript types GENERATED from the database schema. Regenerate after every migration. Never hand-edit.
*   `packages/tokens` — design tokens, single source of truth for both apps. A hard-coded colour or spacing value in app code is a defect.
*   WITHIN the mobile app, shared code still lives where it did: `apps/mobile/lib` for data access, hooks and utils; `apps/mobile/components` for UI and design-system pieces.
*   `apps/mobile/lib` holds the SHARED DATA-ACCESS LAYER — the single doorway between any hub and the spine. A screen talking to Supabase directly is a bug.
*   Promotion rule, within an app: used by two or more hubs, or it touches the spine. Anything touching the spine is shared by definition and belongs in `lib` on day one.
*   Promotion rule, across apps: needed by BOTH `apps/mobile` and `apps/web`, or derived from the database schema. Otherwise it stays in the app.
*   Versioning of shared packages: NONE. Workspace-linked, one commit, one version. No internal package versions to reconcile — the workspace exists for boundaries and type sharing, not for release trains.
*   No secrets in the repo. Supabase keys and future Stripe keys live in `.env`, which is gitignored. `env.example` is committed with keys blank.
*   No mock data merged to main. Fixtures stay local or stay in a branch.

### 6\. Branching, Commits & Migration Discipline

| Aspect | Detail |
| ---| --- |
| Branches | `main` + `feat/*`. Work happens on a feat branch, lands via PR into `main` |
| Commits | SMALL, PRESENT TENSE, one logical change each |
| Commit references | EVERY commit references a ClickUp custom ID — UJGFREE-#### — from list 901110966415 |
| Migration location | `supabase/migrations/` — NOT `/db` |
| Migration naming | TIMESTAMPED and append-only. Format `YYYYMMDDHHMMSS_description.sql` |
| Migration example | `20260826000100_tenancy_and_spine.sql` |
| Migration rule | NEVER edit an applied migration. Fix forward with a new timestamped file |
| Type regeneration | Regenerate `packages/types` after every applied migration |
| RLS rule | The migration that CREATES a table creates its `tenant_id` column AND enables AND forces RLS AND writes its policy IN THE SAME MIGRATION. No table lands unguarded |
| FC-1 rule | EVERY new table gets a new FC-1 isolation case in the SAME pull request |
| Schema before screens | NO UI FOR A HUB until its tables + RLS exist and the migration is committed |
| Secrets | `.env` gitignored, `env.example` committed. Nothing else |
| Mobile build | EAS Build / EAS Update |
| Web build | Next.js deploy for the compliance routes |
| CI | GitHub Actions — runs `scripts/test-rls.sh` |

Why timestamped and not numbered. Sequential numbers collide the moment two branches are open at once, and they carry no information about when a change landed. Timestamps sort identically, never collide, and are what the Supabase CLI generates on its own. The naming is not cosmetic — the CLI orders application by filename, so an off-scheme file applies in the wrong place.

`SUPERSEDED` v1.0–v1.1 · superseded 2026-09-07 · The prior rule read: "`/db` is NUMBERED AND APPEND-ONLY: `0001_init.sql`, `0002_spine.sql`, and so on" with "NEVER edit an applied migration. Fix forward with a new numbered file." The fix-forward half still holds and is carried into the table above. The NUMBERED half and the `/db` location are both wrong now: migrations live in `supabase/migrations/` and are timestamped, as in `20260826000100_tenancy_and_spine.sql`. Do not create `0003_*.sql`. Do not move migrations back to `/db`.

### 7\. Adding a New Hub, Package, or App

1. Write the migration first — new table, its `tenant_id`, RLS ENABLED and FORCED, and its policy, in one timestamped file in `supabase/migrations/`. Commit it.
2. Add an FC-1 cross-tenant isolation case for the new table in `supabase/tests/`, in the SAME pull request. A table without a case is not done.
3. Regenerate `packages/types` so both apps see the new schema.
4. Add the data-access functions for that hub to `apps/mobile/lib`. This is the hub's only route to the spine.
5. Create the hub folder under `apps/mobile/app/` and build screens against `lib` only.
6. Promote any UI reused by a second hub into `apps/mobile/components`; promote anything needed by BOTH apps into `packages/`.
7. Register the hub in the Hub Map (4.1) and the Component Catalog (6.14).

A NEW TOP-LEVEL APP OR PACKAGE REQUIRES AN ADR. `apps/` and `packages/` exist to hold a justified second target and genuinely shared code — not as a dumping ground. Two apps and two packages is the current, deliberate count.

`FUTURE-STATE` — Phase 7 web companion. A full React Native Web surface sharing mobile code would live as its own app under `apps/`, consuming the same `packages/`. That is a new ADR. It is NOT the same thing as `apps/web`, which is compliance pages only and stays that way.

### 8\. Governance

Structure changes go through an ADR (5.3) before any folder moves. That includes adding a top-level app or package, adding a build orchestrator, collapsing the workspace, or reintroducing a dropped tool such as Payload CMS.

Boundary violations — a hub importing a sibling hub, one app importing the other, a screen querying Supabase directly, a hand-edited generated type, an edited migration, a new table without its FC-1 case, a secret or mock dataset in a diff — are caught at PR review by Omegea Hunter. The workspace boundary is the only thing tooling enforces, so the review is the control.

This page is reviewed whenever a new hub ships, a new app or package appears, or an ADR changes the architecture. It is the source of truth for repo layout alongside `CLAUDE.md` at the repo root — and `CLAUDE.md` is generated from 6.2, so the two pages must not contradict each other.

### 9\. Repository Context an Agent Needs Before Touching Anything

SLICE ZERO IS BUILT AND MERGED. Do not rebuild it, do not "add" it, do not assume it is missing.

The tenancy wall is in place: `tenants`, `profiles`, `tenant_members`, `entities`, `areas`, `actions`. Every row carries `tenant_id`. RLS is both ENABLED and FORCED on every table — forced matters, because enabled alone is bypassed by the table owner.

`current_tenant_ids()` is a SECURITY DEFINER helper that carries its own auth check and a pinned `search_path`. Both properties are load-bearing. Do not strip either.

A signup trigger bootstraps profile, tenant, membership, entities and areas on account creation.

`actions_today` is a VIEW with `security_invoker = true`, so it evaluates RLS as the calling user rather than the view owner.

FC-1 is a cross-tenant isolation suite of twelve attacks. It runs in CI via `scripts/test-rls.sh` and passes 12 of 12. It has been verified to DISCRIMINATE — that is, it fails when isolation is deliberately broken, so a green run means something. Every new table gets a new FC-1 case in the same pull request that creates it.
