### 1\. What We're Building

A **multi-tenant personal + freelance life OS** — mobile-first, with a small compliance web surface — that replaces Notion as Omegea's primary operating system for life and business. One database, one repository, fully owned, fully automated.

**A website tells; an application does.** This app **drives action** instead of storing plans. If a feature only records something and never produces an Action, question it.

It is **NOT** a clone of Notion's flexibility. It does the specific things the Notion Omegea Command Center does today — faster, and without Notion's limits.

### 2\. Beta Scope (ADR-0011)

THE BETA IS ACTIONS AND JOURNAL ONLY. That single sentence is what makes most of the deferrals on this page make sense.

Everything below the actions-and-journal line is out of the beta: charts and reporting surfaces, live-updating views, scheduled automation, server-side jobs, and offline use. They are shelved with their tooling, together, on purpose — half a feature with its library already installed is how a scope decision quietly unwinds.

A slice that needs a deferred capability is not a slice to build cleverly around. Stop, and either cut the slice or write the ADR that revives the capability.

### 5\. The Three Structural Rules

These are the rules that break the build if violated. Everything else is style. NONE OF THEM CHANGED on 2026-09-07.

#### Rule 1 — Tenancy on every row

Three nested layers: **tenant** (account — the RLS wall) → **profile** (person — Omegea, each child) → **entity** (business — Empire, UJG, JMR).

*   Every row is scoped by `tenant_id` **always**, plus `profile_id` and/or `entity_id` where relevant.
*   Every Supabase call is constrained by `tenant_id` = the authenticated tenant.
*   **RLS on every table, ENABLED AND FORCED, no exceptions, from day one.** Enabled alone is bypassed by the table owner. A table without a policy is a data leak waiting for the commercial release.
*   Every new table gets a new FC-1 cross-tenant isolation case in the SAME pull request.

#### Rule 2 — Spine first, hubs as lenses

The app is **one record, many views**. The spine — Actions, Events, Money ledger, People/CRM, Goals & Missions, Notes, Areas/Tags, Automation + Notifications, Templates/Routines — is an inherited platform layer used through a shared data-access layer.

*   **No hub reaches into a sibling hub's tables.** Cross-hub needs go through the spine or an explicit interface.
*   Each bounded-context hub owns its own private tables: Productivity · Lifestyle Vault · Academic HQ · Control Room. Command Center is a platform surface — it owns only the Today snapshot and quick-capture inbox, and reads everything.
*   If a feature wants to reach across hubs directly, **stop and flag it** — that's an architecture change, not a quick fix.

#### Rule 3 — Everything decomposes into Actions

Every plan, goal, bill, routine, and ritual becomes an Action carrying a **do-now deep link** to where it gets completed. Progress rolls up from completed Actions — never typed by hand. Anything timed also becomes an Event.

### 6\. Failed-Write Logging (HARD REQUIREMENT, ADR-0012)

Every failed write MUST be logged locally with a timestamp. This is not error-handling politeness. It is measurement infrastructure.

The reason. The project's kill criterion measures DAILY FRICTION. In an online-only beta a write can be lost to flaky wifi, and that is not a design failure — it is a network event that looks exactly like one in the data. Without a local, timestamped log of failed writes, a friction number cannot be separated into "the app is bad" and "the train went into a tunnel," and the beta week cannot be read honestly.

What this means in practice.

*   Every write path catches its failure and appends a local record: timestamp, what was attempted, the error.
*   The log is local and survives app restart. It is not a Supabase table — a write failure is exactly the moment Supabase is unreachable.
*   Nothing is silently swallowed and nothing is silently retried into invisibility. A retry that eventually succeeds still logs the failure that preceded it.
*   The log is reviewed at the end of the beta week alongside the friction numbers.
*   A slice that writes to the database is NOT DONE until its failure path logs.

This requirement stands in for the offline write queue, which is deferred. It is cheaper, and for reading the beta honestly it is the part that actually mattered.

### 7\. How We Work, Session by Session

Omegea works in short, focused, anchored sessions (often 15–30 min, sometimes phone). Build accordingly.

1. **One slice per session.** A slice = one hub's one screen wired end to end (UI → state → Supabase → tested), or one schema migration. **Never leave a slice half-wired.**
2. **Schema before screens.** No UI for a hub until its tables + RLS exist and a migration is committed.
3. **Vertical, not horizontal.** Finish Command Center fully before starting Productivity. Don't scaffold ten empty screens.
4. **Commit at every working state.** Small commits, present tense. Branch per feature, PR into `main`.
5. **State the plan, then build.** Session start: restate task ID, slice, definition of done. Session end: restate what's done and the next slice.
6. **Map work to ClickUp.** Every slice corresponds to a task in list `901110966415`. Reference the custom ID (`UJGFREE-####`) in commits.

### 12\. Patterns to Use

*   **Computation in the database.** Generated columns for row-local math → views for cross-row aggregates → client selectors for view-only display math, in that order. Document any non-trivial calculation when added.
*   **Refetch on focus.** With realtime deferred, a view refreshes when it gains focus. Simple, predictable, and enough for one user on one device.
*   **Fail loudly and log.** Every write path surfaces its failure in the UI and appends to the local failed-write log.
*   **Event rules** — `DEFERRED` per ADR-0011. When X happens, create an Action or send a nudge, into one notification inbox. Needs Edge Functions; not in the beta.
*   **Templates that spawn** — `DEFERRED` per ADR-0011. Reusable bundles auto-create Actions and Events on schedule. Needs `pg_cron`; not in the beta.
*   **Precomputed rollups** — `DEFERRED` per ADR-0011. Reports read snapshots rather than aggregating live. There are no reporting surfaces in the beta.
*   **Optimistic writes** — `DEFERRED` per ADR-0012. Queue offline, reconcile on reconnect, last-write-wins for a single user. The beta is online-only; a write either succeeds now or is logged as failed.

The four deferred patterns above are kept in place because they are the intended design once their capabilities return. They describe the target, not the beta. Do not build them, and do not delete them.

### 13\. Patterns to Avoid (anti-patterns)

| Anti-pattern | Why | Do instead |
| ---| ---| --- |
| Duplicated formulas across screens | The exact Notion failure this app exists to escape | Generated column or view |
| A hub querying a sibling hub's tables | Rots the shared kernel into a distributed monolith | Go through the spine or an explicit interface |
| One app importing the other app | Breaks the workspace boundary the monorepo exists to hold | Promote shared code into `packages/` |
| A table without `tenant_id` + FORCED RLS | One missed policy is a cross-tenant leak | Scope, policy and FC-1 case in the same pull request |
| A record type that never spawns an Action | The app becomes a thing that tells, not one that does | Decompose it into Actions |
| Editing an already-applied migration | Breaks reproducibility | Add a new TIMESTAMPED migration |
| Creating a numbered migration | Wrong scheme. The CLI orders by filename | Use `YYYYMMDDHHMMSS_description.sql` |
| Hand-editing `CLAUDE.md` or `packages/types` | Both are generated. The edit is lost and the sources drift | Change this page or the schema, then regenerate |
| Installing a deferred library to "get ahead" | Reopens a closed scope decision without an ADR | Leave it out. Write the ADR if it truly must return |
| Building an offline cache or write queue | The beta is ONLINE-ONLY per ADR-0012 | Log the failed write with a timestamp |
| Swallowing a write failure | Destroys the friction measurement the beta depends on | Surface it and log it locally |
| Scaffolding many empty screens | Horizontal work leaves nothing finished | One vertical slice at a time |
| Mock data merged to `main` | Hides broken data paths | Real Supabase data before the slice is done |

### 14\. Error Handling

*   Handle **loading, empty, and error** states on every screen — part of the definition of done, not polish.
*   Validate at the boundary with Zod; invalid input rejects with no write.
*   An expired session mid-action must re-auth and **preserve state**.
*   Never swallow a failure silently — surface it in the UI, log it to Sentry, AND append it to the local failed-write log if it was a write.
*   A network failure is a first-class, expected outcome in an online-only beta. Treat it as data, not as an edge case.
*   Third-party services: documented auth, watched rate limits.

`SUPERSEDED` 2026-09-07 by ADR-0012 · "Graceful offline fallback" is deferred with offline support; there is no fallback path to fall back to. It returns with offline-first. `SUPERSEDED` 2026-09-07 by ADR-0011 · "Scheduled jobs fail safely and re-run rather than half-applying" is deferred with scheduled jobs and returns with them.
