### 1\. Overview & Objectives

Life OS App is a multi-tenant personal + freelance life OS built in React Native/Expo on Supabase Postgres. It is built solo by Omegea Hunter with Claude Code as the build agent, so this plan assumes one person wearing every QA hat — no handoff between a dev team and a test team. Formal test work lands in Phase 5 of the roadmap (ClickUp task UJGFREE-5910, "Unit + integration tests for all modules," list 901110966415), which gates Phase 6 launch.

*   **Product / release:** Life OS App — v1 launch build (Phase 6 gate)
*   **Quality objectives:** no cross-tenant data leakage under any condition · the six-item failure chain in section 7 passes on every release · every build slice proven on a real device before its ClickUp task closes
*   **Guiding quality principles:** risk-based — the failure chain is the regression core, not an afterthought · validate at the boundary (Zod) and compute in the database (generated columns and views), so tests assert one source of truth instead of duplicated formulas · manual real-device pass is part of the strategy, not separate from it · load testing deferred until there is commercial load to test

**Performance targets** (single source of truth for this app — draft until measured against a real build):

| Target | Threshold |
| ---| --- |
| App cold start | under 3s |
| Screen interaction | under 100ms |
| Sync / query p95 | under 400ms |
| Offline reads | instant |

### 3\. Scope

**In scope**

*   All modules shipping in the v1 launch build, including the sensitive modules (Intimacy, Spiritual) behind the biometric lock
*   Multi-tenant data access — RLS policies on every table
*   Auth lifecycle: sign-in, session expiry, re-auth, state preservation
*   Offline capture and write conflict resolution on reconnect
*   Scheduled automations and their idempotency
*   Zod validation at every boundary
*   Postgres generated columns and views (computed values)
*   The four critical journeys: capture-to-action, log money, run a routine, complete the day

**Out of scope**

*   Load and stress testing — deferred to pre-commercial, Phase 7 `FUTURE-STATE`. Nothing about single-user traffic justifies the setup cost now.
*   Multi-user concurrent-edit conflict resolution — the app is single-user per tenant, so conflict handling is last-write-wins and multi-writer merge logic does not exist to test.
*   Third-party penetration testing — out of budget pre-revenue; revisit when the app carries client data.

### 7\. Risk-Based Prioritization — Failure → Acceptance → Test

This is the wired spine of the plan and the regression core. Every row runs on every release.

| # | Failure | Acceptance criterion | Test level | Likelihood | Impact | Priority |
| ---| ---| ---| ---| ---| ---| --- |
| 1 | Tenant isolation breach | Given a user, when querying another tenant's row, then RLS blocks it — no leak. RELEASE GATE. | Integration | Med | High | High |
| 2 | Auth expires mid-action | Given an expired session, when acting, then re-auth and state preserved | Integration | High | Med | High |
| 3 | Sensitive module bypass | Given the lock, when opening Intimacy/Spiritual without biometric, then blocked — nothing rendered or cached | Integration | Med | High | High |
| 4 | Offline write conflict | Given two offline edits, when reconnecting, then resolved per last-write-wins (single user) | Integration | High | Med | High |
| 5 | Bad input | Given invalid data, when submitting, then validation rejects — no write | Unit | High | Med | Med |
| 6 | Automation double-run | Given a scheduled job re-fires, when it runs, then idempotent — no duplicate Actions or charges | Integration | Med | High | High |

Case 1 is the only hard release gate: it fails, nothing ships. Cases 2–6 failing block the Phase 6 launch gate but can be triaged inside a build phase.
